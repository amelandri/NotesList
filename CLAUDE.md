# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Obsidian community plugin ("Notes List", id `notes-list`) that opens a custom two-column view: a chronological list of notes from one configurable vault folder on the left, and a GitHub-style contribution heatmap of note activity on the right.

## Commands

- `npm run build` — type-check (`tsc -noEmit -skipLibCheck`), lint (`eslint . --max-warnings 0`; see "Lint" below), then bundle `src/main.ts` → `main.js` via esbuild (production, no sourcemap).
- `npm run dev` — esbuild in watch mode (inline sourcemap), no type-check.
- `npm run install-to-vault` — copies `manifest.json`, `main.js`, `styles.css` into `<vault>/.obsidian/plugins/notes-list/`. Vault path defaults to `/Users/amelandri/Syncthing/TestObsidian`, overridable with `OBSIDIAN_VAULT_PATH`.
- `npm run deploy` — `build` + `install-to-vault`; the normal edit/verify loop for this repo. After deploying, reload Obsidian (`Cmd+R`) to pick up the new `main.js`/`styles.css` — `npm test` (below) covers the plugin's pure logic, but nothing exercises the actual Obsidian integration or rendered DOM, so this manual reload against the live vault is still the only way to verify those.
- `npm run release -- <x.y.z> ["notes"]` (`release.mjs`) — from a clean, up-to-date `dev`: bumps `manifest.json`/`package.json`/`versions.json`, builds, commits "Bump version to x.y.z", tags, pushes `dev` and the tag together (`--atomic`), fast-forwards `main` (never forced), and publishes a GitHub release with `main.js`/`manifest.json`/`styles.css` attached. **Re-runnable with the same version** after a failure partway through: if HEAD is already that bump commit (and the tag, if present, points at it), it skips the bump/commit/tag and continues with the remaining steps. Pushes are no-ops when already done, and an existing GitHub release is reused, with its assets replaced by a fresh build. Pushes retry up to 3 times, 5s apart, because GitHub has been seen rejecting a valid tag push with a bare `! [remote rejected] <tag> (failed)` that succeeded on a plain retry. It refuses to continue if the tag exists but points somewhere other than HEAD. Resuming needs HEAD to still be the bump commit, so don't commit anything else in between; a fix to the script itself has to be run from an uncommitted copy until the release is done.
- `npm run lint` — just the lint step on its own.
- `npm test` — runs the automated test suite (`vitest run`) under `test/`. See "Automated tests" below for what is and isn't covered and why.
- `npm run generate-test-notes -- [count] [folder]` (or `node generate-test-notes.mjs [count] [folder]`) — writes `count` (default 100) throwaway `.md` notes into `<vault>/[folder]` (default `Note`) for load-testing the list/heatmap/tag-tree against a large folder. Same identical multi-paragraph Lorem ipsum body every time (content doesn't affect what's being measured — edit the `BODY` array directly to change its length/shape); `timestamp` frontmatter randomized across the last 6 months; filenames follow the `YYYYMMDDHHmmss` pattern (deduped with a `-2`, `-3`, … suffix on collision), matching this plugin's own default `uniqueNoteNameFormat` (see "Self-contained note creation" below). Dev-only, not part of the shipped plugin — same `OBSIDIAN_VAULT_PATH` override as `copy-to-vault.mjs`.

`npm test` (`vitest run`) runs the automated test suite under `test/` — see "Automated tests" below. `esbuild.config.mjs` marks Node builtins as external to esbuild's bundling via `node:module`'s own `builtinModules` (not the separate `builtin-modules` npm package, which this project used to depend on — Node has exposed the same list natively since well before this project's minimum supported Node version, so the extra package was redundant; a community plugin review flagged it, per the [module-replacements](https://github.com/es-tooling/module-replacements) project). Before cutting a release, verify `package-lock.json` is actually installable with `npm ci` (not just `npm install` — `ci` additionally fails on a lockfile that's drifted from what the registry can still resolve, which `install` alone can silently tolerate by rewriting the lockfile); a stale entry pinning a since-removed transitive dependency version is exactly what broke the automated review's own dependency install once, and `npm install` alone didn't surface it.

### Lint — keeping the community plugin review's warnings from coming back

`eslint.config.mjs` runs `eslint-plugin-obsidianmd`'s `recommended` config, the Obsidian team's own rule set that the community plugin review uses (ESLint core, typescript-eslint type-checked rules, and Obsidian-specific rules such as `obsidianmd/ui/sentence-case` and `depend/ban-dependencies`). It runs on `src/` and `package.json`; dev scripts (`*.mjs`), `test/` and `main.js` are ignored. It's part of `npm run build`, so `deploy` and `release` can't skip it. `--max-warnings 0` makes warnings fail the build too, because the review reports warnings and the sentence-case rule, for one, is only a warning. Fix what it reports rather than configuring it away: an exception here (e.g. the sentence-case rule's `brands` option) wouldn't apply in the review, which runs the defaults. That's why the ribbon tooltip is "Open notes list", not "Open Notes List".

The official config alone doesn't reproduce two ways this project has passed lint locally but failed in the review, because both depend on the review's environment resolving fewer types than a local install. Two extra guards cover them:

- **Newer built-ins** (`String.prototype.trimEnd`, ES2019, was the real case): locally `@types/node` quietly declared them, so `tsc` passed even though `lib` didn't include them; in the review they typed as `error` and tripped `no-unsafe-call`. `tsconfig.json` now sets `"types": []`, so no `@types/*` package is pulled in implicitly and `tsc` itself fails on any built-in `lib` doesn't cover (`lib` includes `"ES2019"` for `trimEnd`). Add the matching `lib` entry when `tsc` reports a "does not exist on type … try changing the 'lib' compiler option" error; it's type-only, and Obsidian's Electron/mobile engines support these natively. (`src/` needs no Node types: it runs in Obsidian's renderer, and DOM covers timers etc.)
- **`moment`**: see the `src/moment.ts` note below. A `no-restricted-imports` rule fails lint on importing `moment` from `"obsidian"`, or from the `moment` package itself, anywhere in `src/` except `src/moment.ts`.

Each guard was verified by reintroducing its original error in a scratch copy and confirming `npm run build` fails: `moment` imported from `"obsidian"`, an ES2021 built-in (`replaceAll`), an untyped `processFrontMatter` callback, an unnecessary `as` assertion, a Title Case UI string, and `moment` re-added as a dependency. The clean tree builds with zero problems.


**`src/moment.ts` — why no source file imports `moment` from `"obsidian"` directly.** `obsidian.d.ts` types its `moment` export via `import * as Moment from 'moment'`, and the community plugin review's lint environment can't resolve that import. `moment` then types as `error`/`any` there, and every `moment()`-derived value trips the whole `@typescript-eslint/no-unsafe-*` family (`-assignment`, `-call`, `-member-access`, `-argument`, `-return`: dozens of hits across `heatmap.ts`/`main.ts`/`view.ts`). Declaring `moment` as a devDependency was tried first and did **not** fix it in the review. `src/moment.ts` therefore declares its own minimal `Moment` interface (only the methods this plugin actually calls) and re-exports Obsidian's `moment` cast to it (`as unknown as MomentFactory`), so type checking no longer depends on the `moment` package's typings resolving at all. Runtime is unchanged: it's still Obsidian's own bundled moment instance. Everything in `src/` imports `Moment`/`moment` from `./moment`. To call a moment method not yet declared there, add it to the interface first, matching moment's real signature. This was verified locally with typed ESLint (`recommendedTypeChecked`) in three setups: `moment` resolving normally, `moment` missing (`error` type), and `moment` stubbed as `any`. The old code reproduced every warning family in the `any` setup; the new code is clean in all three. `moment` is deliberately **not** a direct dependency: it was briefly added as a devDependency, which didn't fix the review and is itself flagged by `depend/ban-dependencies`. `test/obsidian-mock.ts` and the tests still import the real package, which is installed transitively as a dependency of `obsidian`.

## Architecture

- `src/main.ts` — `Plugin` entry point. Registers the `ItemView`, a ribbon icon + command to open it (`id: "open"`, `name: "Open"`), a second command to create a new note (`id: "create-new-note"`, `name: "Create new note"` — see "Self-contained note creation" below — deliberately no default hotkey, per Obsidian's own plugin guidelines; the user assigns one from Settings → Hotkeys), and the `PluginSettingTab`. Neither command's `id`/`name` repeats the plugin's own id (`notes-list`) or name (`Notes List`) — Obsidian already prefixes every command with the plugin name in the command palette (`"Notes List: Open"`) and namespaces ids internally, so doing it again here is redundant and is flagged by the community plugin review as such (an earlier version had `id: "open-notes-list"`, `name: "Open Notes List"`). Also wires vault (`modify`/`create`/`delete`/`rename`) and `metadataCache` (`changed`) events to a debounced `requestRefresh()` that re-renders any open `NotesListView` leaf. `onVaultEvent(file, oldPath?)` first checks `isInScope()`, which mirrors `NotesListView.getNotesInScope()`'s own folder/subfolder logic exactly (not a bare `path.startsWith(folderPath)`, which would also match e.g. `NotesArchive/x.md` against a `Notes` folder setting) — for `"rename"` specifically, both the new `file.path` **and** the passed `oldPath` are checked, since a note renamed/moved *out* of the watched folder only has its new (now out-of-scope) path by the time the handler runs, and checking only that would leave the stale entry showing until an unrelated event happened to trigger a refresh. Settings persist via `loadData`/`saveData` (`data.json` in the plugin folder), merged over `DEFAULT_SETTINGS` — but only *after* `loadSettings()` first runs the raw loaded data through `migrateSettings()` (see "Settings migrations" below), so `Object.assign` always merges an already-current shape. `loadSettings()` also runs `settings.folderPath` and `settings.templatePath` through the module-level `normalizeOptionalPath()` (Obsidian's own `normalizePath()`, with `""` special-cased ahead of it since `normalizePath("")` returns `"/"`, which would break the `""` = "entire vault"/"no template" sentinel both settings rely on) — both on every load (so a value saved before this normalization existed still gets cleaned up) and again in each setting's own `onChange`. Because of that, `isInScope()` and `getNotesInScope()` (in `view.ts`) both read `settings.folderPath` directly with no further trimming; the old inline `.replace(/^\/+|\/+$/g, "")` duplicated in both places is gone. There's deliberately no `onunload()` override: Obsidian's own plugin guidelines call out detaching a plugin's leaves there specifically, since the same `onunload` path also runs on a plugin *update* (not just a manual disable) — detaching would close the user's open Notes List tab on every update instead of letting it quietly reinitialize once the plugin reloads.
- `src/settings.ts` — the `NotesListSettings` shape and defaults: `folderPath`, `includeSubfolders`, `contentDisplay` (`ContentDisplayMode`: `"full" | "preview"`), `previewLength`, `notesPerPage`, `showNoteName` (`ShowNoteNameMode`: `"never" | "always" | "whenDifferent"`), `showDateGroups`, `uniqueNoteNameFormat` (a moment.js format string), `templatePath` (empty = no template; see "Self-contained note creation" below). Pin state is *not* here — see "Pinned notes" below.
- `src/view.ts` — the `ItemView` (`VIEW_TYPE_NOTES_LIST`). `refresh()` (rescans every note in scope, expensive) and `render()` (rebuilds the DOM from scratch — `contentEl.empty()` then re-render, rather than diffing — from the already-scanned `cachedEntries`, cheap) are separate for performance at scale; see "`refresh()` vs `render()`" below.
- `src/moment.ts` — locally-typed re-export of Obsidian's `moment` (see the note under Commands for why).
- `src/heatmap.ts` — pure DOM-rendering function `renderHeatmap(container, dates, selection)`, no plugin/view state (`selection: HeatmapSelection` bundles `selectedDate`/`onSelectDate`/`selectedMonth`/`onSelectMonth` — grouped into one object once the parameter list grew past a couple of callbacks). Buckets note counts per day into a 6-month, GitHub-style week/weekday grid; every real (non-future) day cell gets a tooltip and a click handler calling `onSelectDate` with its `"YYYY-MM-DD"` key (`.is-selected` when it matches `selectedDate`), and the (one per month) visible month label gets a click handler calling `onSelectMonth` with its `"YYYY-MM"` key (`.is-selected`/`.is-clickable` likewise). The legend row ends with `.notes-heatmap-total`, pushed to the row's right edge with `margin-left: auto` since `.notes-heatmap-legend` is a flex row. `renderHeatmap`'s new `visibleCount` parameter (the caller's already-filtered count, e.g. `visibleEntries.length` in `view.ts`) is compared against `dates.length` (every note in scope, unfiltered, not just the ones inside the 6-month window): equal → just the total; otherwise → `"{visibleCount} of {total} notes"`. No separate "is a filter active" flag is threaded through — the two counts simply differing is what drives the "of" format, so it stays correct by construction even if a new filter kind is added later. `maxCount` (the color-scale divisor for `levelFor()`) is computed only from days actually drawn in the visible `start..today` window, not from every entry in `dayCounts` — `dates` includes every note in scope regardless of age, so a single outlier day outside the 6-month window (e.g. a bulk import) would otherwise dominate `maxCount` and flatten every visible cell's contrast down near "Less" even on the grid's own busiest day.
- `src/tagTree.ts` — pure functions for the tag browser: `buildTagTree(perNoteTags)` takes **one tag array per note** (not a pre-flattened list — see "Tag note counts" below) and groups `#a/b/c`-style tags (as returned by `getAllTags`) into a nested `TagTreeNode` map by splitting on `/`, each node also carrying a `count`; `renderTagTree(container, root, selectedPath, collapsedPaths, onSelect, onToggleCollapse)` renders it as nested, collapsible `<ul>`s (a chevron toggle appears only on nodes with children), each label suffixed with `(count)`; `tagMatchesFilter(tag, filter)` implements Obsidian's usual hierarchical tag semantics (selecting a tag also matches its sub-tags), matching **case-insensitively** to mirror Obsidian's own tag pane, which treats `#Project` and `#project` as the same tag. That merge happens in two places: `getOrCreateChild()` keys `TagTreeNode.children` by the segment's lowercased form (whichever casing is seen *first* wins for that node's displayed `segment` and its `path`, which doubles as the filter value passed to `tagMatchesFilter`), and `buildTagTree()`'s per-note `reachedPaths` is keyed by lowercased path too, so a single note carrying both `#Project` and `#project` still only increments that node's count once, not twice.
- `styles.css` — all view styling, loaded automatically by Obsidian alongside `main.js`/`manifest.json`.

### Automated tests

`test/*.test.ts` (Vitest, `npm test`) cover this plugin's pure logic — parsing, matching, counting, migrating — directly, with no Obsidian instance and no DOM. What they deliberately **don't** cover: `NotesListView.render()`/`renderEntry()`, the settings tab's rendering (Obsidian draws it from `getSettingDefinitions()`; `validatePositiveInteger()` is the one testable piece), `createUniqueNote()`'s actual vault/frontmatter/API calls, or anything else that genuinely needs a live Obsidian environment — that's still what the manual `npm run deploy` + reload loop is for (see Commands above).

The real `obsidian` npm package ships **no runtime at all** — `node_modules/obsidian/package.json`'s `"main"` is empty; it's type declarations only, resolved by the real app at plugin load time. Importing a `src/*.ts` file that does `import { ... } from "obsidian"` would crash immediately in a plain Node test process for want of anything to import. `test/obsidian-mock.ts` stands in for it, wired up via `vitest.config.ts`'s `resolve.alias` (test-only — `esbuild.config.mjs` still marks `"obsidian"` external for the actual plugin build, completely unaffected by any of this). It re-exports the *real* `moment` package (already a genuine transitive dependency of `obsidian` itself, and this project's date logic depends on its exact behavior — a fake would defeat the point of testing it), and otherwise provides bare, no-behavior stubs (`ItemView`, `Plugin`, `TFile`, `Notice`, etc.) — just enough that a module *imports* without throwing; nothing in the mock is meant to emulate Obsidian's real UI/vault behavior, so no test relies on it doing anything beyond existing.

A handful of functions were hoisted out of `NotesListView`/`NotesListPlugin` methods into plain module-level `export`ed functions specifically so tests could call them directly, without constructing a (heavily mocked) view/plugin instance first — in every case this was a *pure, behavior-preserving* move, not a redesign: each one was already private and didn't reference `this` at all (`parseDatetime()` and `dateGroupLabel()`, both formerly on `NotesListView`; `resolveUniqueNoteNameFormat()`, extracted from the one line of logic inside `NotesListPlugin.uniqueNoteNameFormat()` that doesn't touch `this.settings` beyond its own parameter). `dateGroupLabel()` also gained a `now: moment.Moment = moment()` parameter (defaulting to the real current time for every existing call site, so production behavior is unchanged) purely so tests can pin "today" to a fixed instant instead of a result that depends on which real day the suite happens to run on. `heatmap.ts`'s day-bucketing and window-scoped max-count logic (`countByDay()`, `computeVisibleMaxCount()`) and `levelFor()` were similarly split out of `renderHeatmap()`'s body into their own exported functions — `renderHeatmap()` itself still isn't tested directly (it's pure DOM construction), but the color-scale math that was the actual source of a real bug this session (an outlier day outside the visible window skewing every visible cell's contrast) now is.

### Note dating convention

A note's date/time comes from its **frontmatter**: `resolveDate()` in `view.ts` reads a single `timestamp` property via `metadataCache.getFileCache(file)?.frontmatter`, meant to be set through Obsidian's own **"Date & time"** property type (Properties panel → type dropdown), not typed by hand. This replaced an earlier two-field `date`/`time` convention — see "Legacy `date` fallback" below for what still reads from old notes. It's deliberately *not* called `datetime` — that's Obsidian's own fixed internal name for the property *type* itself (see "Self-contained note creation" below), and naming the property the same thing made error messages read like a tautology ("the `datetime` property must be of type datetime").

Obsidian's own property picker, verified directly by extracting `obsidian.asar` from a real install (`/Applications/Obsidian.app/Contents/Resources/obsidian.asar`, **not** the tiny launcher `app.asar` next to it) and reading its actual formatting code, always writes this value as a **quoted string in local wall-clock time**: `"YYYY-MM-DDTHH:mm:ss"` (its date-only "Date" property type writes the same way, just `"YYYY-MM-DD"`). Concretely: `AA(date)` formats the date part via `date.getFullYear()`/`getMonth()`/`getDate()` (all local accessors, confirmed by grepping the bundle — it contains zero calls to any `getUTC*` accessor), `PA(date)` formats `HH:mm:ss` the same way, and the picker's own `toString()` is `time ? AA(date)+"T"+PA(date) : AA(date)`. That result is a plain JS string, and reproducing Obsidian's own frontmatter write with the `yaml` npm package (`YAML.stringify({ timestamp: "2026-09-25T16:20:00" }, { schema: "yaml-1.1" })`) confirms the library quotes it automatically — because *unquoted*, YAML 1.1 would resolve that same text as a timestamp. So the property picker's output is immune to every quirk below by construction: no auto-cast, no UTC conversion, nothing to defend against.

`parseDatetime()` handles the value defensively anyway, for a value typed by hand straight into the raw YAML (bypassing the property picker and its quoting):

- **String** (the normal case): parsed strictly against `["YYYY-MM-DDTHH:mm:ss", "YYYY-MM-DDTHH:mm", "YYYY-MM-DD"]` — local time, at face value, no conversion.
- **Neither a string nor a `Date`** (a YAML number, a list, …): rejected outright (`null`, so `resolveDate()` falls through to its next fallback) via an explicit `raw instanceof Date` check — not handed to `moment()`, which would e.g. read a bare number as epoch milliseconds. That check is also what lets `moment(raw)` be called without an `as moment.MomentInput` assertion on an `unknown` value, which the community plugin review flagged as unnecessary (in its environment `moment` resolved as `any`; see the `src/moment.ts` note under Commands).
- **A native JS `Date`** (from an *unquoted* value — YAML 1.1's timestamp resolver auto-casts it, same mechanism this section used to document at length for the old `date`/`time` fields): a bare, time-less `timestamp: 2026-09-25` always resolves to *exactly* UTC midnight, with no exceptions (`Date.UTC(year, month, day)` — hour/minute/second default to `0` whenever the source text carries no time-of-day at all), so `parseDatetime()` forces `.startOf("day")` (local midnight) only when `date.clone().utc().format("HH:mm:ss") === "00:00:00"` — converting that instant to local time for display would otherwise print a spurious non-midnight local hour (e.g. 01:00/02:00) purely as a timezone artifact. Checking the *UTC* time-of-day, not the local one, is what tells that apart from a genuinely combined, unquoted `timestamp: 2026-09-25 16:20:00` (also accepted by the same resolver, with a real, non-midnight time-of-day baked in) instead of stomping on it too. **Residual limitation**: that unquoted-combined case is still interpreted as UTC, not local (the resolver has no notion of "local time"), so its time-of-day comes out shifted by whatever the runtime's UTC offset is — typing it unquoted is what causes this; the property picker's own quoted output never hits this path at all.

If `timestamp` is missing, or doesn't parse, `resolveDate()` falls back to `file.stat.mtime` (last-modified time, not creation time — an edit with no explicit `timestamp` set will keep shifting the note's position in the list and its heatmap day). The heatmap consumes the same resolved dates, so it always agrees with the list's ordering. Note this is unrelated to the filename format a newly created note gets (see "Self-contained note creation" below) — that's only about note *creation*, not dating.

#### Legacy `date` fallback

Before `timestamp`, this plugin read two separate frontmatter properties, `date` and `time`. That's gone — `time` is no longer read at all — but `resolveDate()` still falls back to a plain `date` property (via the same `parseDatetime()`, so it's read as a **date only**, never combined with any leftover `time` value) when `timestamp` isn't set, so existing notes written under the old convention don't silently lose their date entirely and fall all the way through to `file.stat.mtime`. There's no equivalent fallback for the old `time` field — a note relying on it shows at local midnight until it's updated to use `timestamp` instead (via Obsidian's own Properties panel, ideally, so it's written correctly-quoted).

`generate-test-notes.mjs` (see Commands above) writes the new `timestamp` convention, quoted, matching Obsidian's own picker exactly (`formatFrontmatterTimestamp()`) — it no longer generates the old two-field shape.

### Content display

`resolveContentDisplay(fm)` in `view.ts` picks the effective mode for a note: its own `content-display` frontmatter property if it's exactly `"full"` or `"preview"`, otherwise `settings.contentDisplay`. `renderEntry()` only truncates the rendered body (to `settings.previewLength` characters) when the resolved mode is `"preview"` — `"full"` always renders the whole body. There's no magic-number sentinel (no `0` meaning "full"); the mode and the length are separate settings.

The cut itself is `truncateMarkdown(body, previewLength)`, not a bare `slice()`: it never cuts through a fenced code block (```` ``` ````/`~~~`) or a GFM table, since either renders broken when truncated partway (an unclosed fence swallows the rest of the preview as code; a table loses rows mid-way). `findUnbreakableBlocks()` scans the body line by line and returns each such block's `[start, end)` range. A fence closes only on the same character repeated at least as many times, and an unclosed fence runs to the end of the body, as Obsidian renders it. A table is a line containing `|` followed by a delimiter row that also contains a pipe, so a bare `---` setext underline or thematic break isn't mistaken for one. The table then extends until a blank line or a line with no `|`. Because the scan is sequential, a table-looking block inside a code fence counts only as code. If `previewLength` lands strictly inside a block, the cut moves to that block's end, so a preview can run longer than `previewLength` by up to one block. The ellipsis then goes on its own paragraph (`"\n\n…"`) rather than inline: appended to a closing fence (```` ```… ````) it would stop that line being a valid closing fence, and appended to a table's last row it would end up inside a cell. If the block is the last thing in the body, the whole body is returned with no ellipsis at all. A cut outside any block behaves as before, with the ellipsis inline. Both functions are covered in `test/view.test.ts`.

Double-clicking anywhere in `.notes-list-content` opens the note, same as clicking the date link (`openNote()`, a closure shared by both so they can't drift apart) — except when the double-click lands on an `<a>` or `<button>` inside the rendered body (`evt.target.closest("a, button")`), since the note can itself contain internal/external links, or a code block's copy button, that already handle their own click, and a double-click landing on one would otherwise also fire this handler on top of whatever the link itself does.

### Settings migrations

`migrateSettings(data)` (`settings.ts`) mutates the raw object `loadData()` returns — whatever shape it happens to be, which for an old enough `data.json` may include fields no longer in `NotesListSettings` at all — up to the current shape, in place, before `main.ts`'s `loadSettings()` ever merges it over `DEFAULT_SETTINGS`. `SETTINGS_MIGRATIONS` is an array of one function per past shape change, each one assigned to the settings version it migrates *from* by its position in the array (index `0` migrates a file with no `settingsVersion` field at all — i.e. every file saved before this framework existed — from version 0 to 1, and so on); `migrateSettings()` runs every migration from the file's own saved version (defaulting to `0` when the field is missing) up through the array's end, so a very old file runs all of them in sequence and a current file runs none. The current version is simply `SETTINGS_MIGRATIONS.length` — `DEFAULT_SETTINGS.settingsVersion` reads it directly, so there's nothing to keep in sync by hand when a new migration is appended.

The first entry replays a change already made once, by hand, earlier in this project: an old `contentPreviewChars` number (`0` meant "show full content"; anything higher meant "preview", truncated to that many characters) was split into today's `contentDisplay`/`previewLength`. No real user's `data.json` was ever affected by that specific rename (nobody outside this one dev vault ever ran the version that had it, and this vault's copy was fixed by hand at the time) — the migration exists so the *pattern* is established before this plugin has real users, not to repair that particular file. `loadSettings()` persists the migrated result immediately (`migrateSettings()`'s return value says whether anything actually changed) rather than waiting for the next unrelated settings edit, so a legacy field doesn't linger in `data.json` indefinitely once it's actually been migrated.

If you change the shape of `NotesListSettings` again, append a new function to the end of `SETTINGS_MIGRATIONS` — never edit or remove an old one, since a file could in principle still be sitting at any past version.

### Settings tab layout

`NotesListSettingTab` uses Obsidian's **declarative settings API**: `getSettingDefinitions()` returns plain definition objects and Obsidian renders them itself — there is no `display()` at all. This is what makes every setting show up in Obsidian's in-app settings search (a community plugin review flagged its absence), and it's **why `manifest.json`'s `minAppVersion` is `"1.13.0"`**: the API doesn't exist before that, and deliberately no imperative `display()` fallback is kept for older versions, since that would mean defining every setting twice (name, description, persistence) with the two copies free to drift apart. Don't lower `minAppVersion` without bringing such a fallback back. The definitions are typed `SettingDefinitionItem<keyof NotesListSettings>[]`, so each control's `key` must be a real settings field.

The definitions form two `type: "group"` entries, each with a `heading`:

- **"Folder and files"**: **Folder** (`folder` control) + **Subfolders** (toggle) — where notes are found — then **Template** (`file` control, `filter` limited to `.md`; see "Self-contained note creation" below) and **Unique note name format** (text) — how a *new* note gets created. All four ended up in one group because they're all about the note's location/identity (where it lives, what shape it starts with, what it's named), as opposed to "Notes display"'s per-render concerns.
- **"Notes display"**: **Show note name** (dropdown), **Content display** (dropdown), **Preview length** (number) — always enabled, even though it only affects rendering when Content display (or a note's own `content-display` override) resolves to `"preview"`; it's independent of that other setting rather than reactively disabled — **Show date group headers** (toggle; see "Date group headers" below) — and **Notes per page** (number), grouped here too since it's just as much a "how the list displays" control as the others. Each dropdown's `options` object carries `satisfies Record<ShowNoteNameMode | ContentDisplayMode, string>`, so adding a new mode to either union without a matching option is a type error.

The built-in `folder`/`file` controls bring Obsidian's own vault suggesters, which replaced this plugin's former hand-rolled `FolderSuggest`/`TemplateSuggest` (`AbstractInputSuggest` subclasses, now deleted). The `file` control persists the full path including `.md`, exactly the same format `TemplateSuggest` used to write, so existing `templatePath` values keep working. `folder` leaves `includeRoot` at its default (`false`), since the vault root is already expressed as `""` ("entire vault") and root-as-`"/"` would break that sentinel. Both `number` settings use `min: 1`/`step: 1` plus the exported `validatePositiveInteger()` as `validate`: returning a message rejects the value (shown inline under the setting) instead of persisting it. This replaced the old `bindClampedNumberInput()` helper, which clamped on every keystroke and only re-synced the displayed text on `blur`, to work around an earlier bug where the field couldn't be cleared mid-edit. The framework now owns that input handling.

`getControlValue()`/`setControlValue()` are both overridden instead of relying on `PluginSettingTab`'s defaults. `setControlValue()` writes the value into `plugin.settings` and then always calls `plugin.saveSettings()`, not just `saveData()`, because only `saveSettings()` also triggers `requestRefresh()` to re-render any open Notes List view. It also runs `folderPath`/`templatePath` through `normalizeOptionalPath()`, the same normalization `loadSettings()` applies on every load.

Both group headings deliberately avoid the word "settings" (the group is *itself* the settings tab, so a heading like "Folder settings" would be redundant) and use sentence case, not Title Case — both straight from Obsidian's own plugin guidelines for the settings tab; the groups formerly named "Folder settings" and "Notes Display" were renamed to "Folder" (later "Folder and files", once **Template** and **Unique note name format** joined it) and "Notes display" for exactly this reason.

### Show note name

`shouldShowNoteName(file)` in `view.ts` decides whether `renderEntry()` appends the file name below the date link (`.notes-list-title`): `"never"`/`"always"` are direct; `"whenDifferent"` (the default) shows the name only when `!isUniqueNoteName(file.basename, format)` — i.e. the file has been renamed away from the pattern `NotesListPlugin.uniqueNoteNameFormat()` resolves to (`settings.uniqueNoteNameFormat`, or `DEFAULT_UNIQUE_NOTE_NAME_FORMAT` — `"YYYYMMDDHHmmss"`, from `settings.ts` — when that setting is blank). That method lives on the *plugin*, not the view (`main.ts`, alongside `createUniqueNote()` — see "Self-contained note creation" below), so both note creation and "whenDifferent" detection share one source of truth without the view needing a plugin-internal method call to reach it.

### Self-contained note creation — no "Unique note creator" dependency

The list header's "New Note" button used to invoke Obsidian's core plugin **"Unique note creator"** (internal id `zk-prefixer`) via an undocumented `app.commands.executeCommandById()` surface, and separately read *its* configured naming format for the "whenDifferent" check above — meaning the button silently failed if that core plugin was disabled, and the "when different" mode's detection changed behavior depending on a setting living in a completely different plugin. Neither is true anymore: **this plugin owns note creation and naming entirely, with no dependency on any other plugin being installed or enabled.**

`createUniqueNote()` (and its helpers `uniqueNoteNameFormat()`, `resolveTemplateContent()`) live on `NotesListPlugin` in `main.ts`, not on `NotesListView` — deliberately, so the exact same logic backs both the view's "New Note" button (`newNoteButton.addEventListener("click", () => void this.plugin.createUniqueNote())`) **and** the `"create-new-note"` command registered in `onload()`, which the user can bind to a hotkey from Settings → Hotkeys (no default hotkey is set — see the `main.ts` architecture bullet above for why). The command's callback works with no Notes List view open at all, since nothing it touches (`app`, `settings`) is view-specific.

`createUniqueNote()` now:

1. Resolves the starting content via `resolveTemplateContent()` (below) — empty string if `settings.templatePath` isn't set, the template note's raw content otherwise. Returning `null` (a misconfigured template) aborts the whole operation before anything is created or written — see below.
2. Creates the watched folder (`settings.folderPath`) first if it doesn't exist yet, so the button works even the very first time a folder is configured.
3. Generates the file name itself: `moment().format(uniqueNoteNameFormat())`, passed through `sanitizeFilenameSegment()` (swaps filesystem-illegal characters — `\ / : * ? " < > |` — for a hyphen, since a custom format string could otherwise place e.g. a literal `/` straight into the name and silently create the note in a subfolder). Collisions get a `-2`, `-3`, … suffix, same convention as `generate-test-notes.mjs`.
4. Creates the note directly inside the watched folder (`vault.create()`), so it immediately shows up in the list — not wherever Obsidian's own global "default location for new notes" setting happens to point.
5. Sets `timestamp` to now via `processFrontMatter()` (same safe API as `pinned`), formatted `"YYYY-MM-DDTHH:mm:ss"` — a plain JS string, which Obsidian's own frontmatter writer quotes automatically for the same reason described in "Note dating convention" above. This overwrites whatever placeholder value the template's own `timestamp` property held, while leaving every other property/line the template contributed untouched.
6. Calls `internalMetadataTypeManager(app).setType("timestamp", "datetime")` — the first argument is *our* property name, the second is Obsidian's own fixed internal widget-type name for its "Date & time" picker (an undocumented internal surface, `app.metadataTypeManager`, verified in app.js, that's what Obsidian's own Properties panel calls the moment a property is set through it, persisted to `.obsidian/types.json`). Calling it ourselves means the Properties panel shows the proper date+time picker for `timestamp` immediately, even in a brand new vault with no prior `timestamp` property anywhere and no template configured. This call is wrapped in its **own** try/catch (`console.warn` only, no `Notice`), separate from the outer one around the rest of the method: by this point the note has already been created and correctly dated, so a failure here — the one undocumented-API call in this method that could plausibly break in a future Obsidian release — should degrade to "no auto-registered picker widget," not be reported as "failed to create the note," which would be actively misleading since the note already exists on disk.
7. Opens the new note in the active leaf.

Any failure along the way (folder creation, file creation, frontmatter write) is caught and surfaced as a `Notice` plus a `console.error`, rather than the button silently doing nothing.

#### Template validation

`settings.templatePath` (empty by default — a blank note) points at any markdown note, picked with the settings tab's built-in `file` control (see "Settings tab layout" above). `resolveTemplateContent()` enforces one rule when it's set: the template's own frontmatter must already contain a `timestamp` key — any value, since it's about to be overwritten with "now" regardless — checked via `metadataCache.getFileCache(templateFile)?.frontmatter`, not by parsing raw text. Two distinct failures each abort note creation with their own `Notice` (returning `null`, which `createUniqueNote()` treats as "stop, create nothing" rather than silently falling back to a blank note): the configured path doesn't resolve to a `TFile` at all (deleted/renamed/mistyped since the setting was last saved), or it resolves but has no `timestamp` property. The template's raw content (read via `vault.cachedRead()`, not `metadataCache`, since this is the one place this plugin needs a note's actual body/frontmatter *text*) becomes the new note's starting content verbatim — `processFrontMatter()` then only touches the one `timestamp` key on top of it.

### Tag, date and month filtering

`NotesListView.selectedTag`, `selectedDate`, `selectedMonth` and `collapsedTagPaths` are transient view state (not persisted to `data.json` — all reset when the view is closed/reopened). `selectedTag` is set from the tag tree under the heatmap panel; `selectedDate` (`"YYYY-MM-DD"`) and `selectedMonth` (`"YYYY-MM"`) are set by clicking a heatmap day cell or a month label, respectively. All three are cleared independently, each via the `x` on its own filter pill in `.notes-list-active-filters` (below the heatmap, `renderFilterPill()` shared by all three) — there's no toggle-off-by-clicking-again anywhere (tag tree, day cell, or month label), by design, so removal always goes through the pill. That container is always created, even with none of the three set, specifically so the Tags section below it doesn't shift up/down as filters are toggled: with nothing active it gets `.is-empty` (`visibility: hidden`, which — unlike `display: none` — keeps its layout box) and one placeholder pill from `renderFilterPill()` (real markup, just invisible) so its reserved height matches an actual pill's rather than a guessed fixed value. `render()` always builds the tag tree and the heatmap from the *full* unfiltered `cachedEntries` (aliased `allEntries` inside `render()`); only the main notes list (`visibleEntries`) is filtered down to notes matching `selectedTag` (via `tagMatchesFilter`) **and** `selectedDate` (exact match on `entry.date.format("YYYY-MM-DD")`) **and** `selectedMonth` (exact match on `entry.date.format("YYYY-MM")`) when set — all three combine with AND, and any subset can be active at once (e.g. selecting a day inside a selected-but-different month just yields an empty list — the pills stay visible so it's clear why, rather than the filters silently overriding each other). The tag index and activity heatmap stay stable reference points regardless of the current filter. Clicking a tag-tree node's chevron toggles its path in/out of `collapsedTagPaths` and calls `render()` again like any other interaction (the view always rebuilds its whole DOM rather than patching just the tree — see `src/view.ts`'s `render()`).

### Tag note counts

Each tag-tree node shows `(count)` — the number of *distinct notes* matching that tag or one of its nested sub-tags, counted across the **full unfiltered** `allEntries` (same semantics as `tagMatchesFilter`, which the actual filtering uses) — same as the heatmap, the tag tree stays a stable reference point regardless of the current date/month filter, so it does **not** narrow when one is active. Clicking a node combines with any active date/month filter via AND (see "Tag, date and month filtering" above), so it can show *fewer* notes than the count displayed when one of those is also selected — the count is "how many notes carry this tag", not "how many notes clicking it will show right now". This is why `buildTagTree()` takes `allEntries.map((e) => e.tags)` (one array per note) rather than the flattened `allEntries.flatMap((e) => e.tags)` it used before counts existed: with a flat list, a note tagged both `area` and `area/work` would count twice towards `area`'s total. Per note, `buildTagTree()` first collects the *set* of every ancestor path any of its tags reaches (e.g. `area/work` contributes both `"area"` and `"area/work"` to that set), then increments each of those nodes' `count` by exactly 1 — so a note can only ever contribute once to a given node, however many of its tags happen to fall under that node.

### Pinned notes

Pin state is a `pinned: true`/`pinned: false` property in the **note's own frontmatter**, not plugin data — so it needs no separate storage, survives renames/moves/copies for free (it's part of the file), and is visible/editable directly in the note like any other property. `NotesListPlugin.setPinned(file, pinned)` writes it via `app.fileManager.processFrontMatter()`, Obsidian's own safe read-modify-write helper (creates the frontmatter block if the note doesn't have one yet). Obsidian types that callback's `frontmatter` parameter as `any`, so both `processFrontMatter()` call sites (`setPinned()` and `createUniqueNote()`) annotate it explicitly as `Record<string, unknown>` — otherwise every `frontmatter.x = ...` trips `@typescript-eslint/no-unsafe-member-access`, which the community plugin review flagged. `NoteEntry.pinned` is populated in `rebuildEntries()` from `cache?.frontmatter?.pinned === true`, the same way `date`/`tags` are — a strict `=== true` check, not a truthiness check, so any other value (a string, `1`, etc.) reads as unpinned rather than guessing at intent.

The button itself renders Lucide's `bookmark` icon (not `pin`) regardless of state, and carries Obsidian's own **`clickable-icon`** class (`is-active` when pinned, in place of a custom `is-pinned` class on the button specifically — the row itself still gets `.notes-list-item.is-pinned`, a separate, unrelated concern) rather than reinventing muted/bold-on-hover/active states from scratch. This isn't just a style preference: verified directly by inspecting Obsidian's own bundled `app.css`, a plain custom class alone (no `clickable-icon`) matches its generic `button:not(.clickable-icon)` reset — one type selector plus a `:not()` pseudo-class, which counts as its argument's specificity (a class), so its total specificity beats a single custom class outright, regardless of load order. That's why every color/background rule here used to need `!important` to win at all. Adding `clickable-icon` sidesteps the fight entirely (that reset no longer matches), and its own base/`:hover` rules already provide `var(--icon-color)` at rest and `var(--icon-color-hover)` on hover for free — only the accent-when-pinned color (`.notes-list-pin-button.is-active { color: var(--text-accent); }`) is still layered on top, and even that doesn't need `!important`: it ties on specificity with Obsidian's own `.clickable-icon.is-active` rule (two classes each), and wins on source order since this plugin's stylesheet loads after Obsidian's own. `cursor: pointer` is still explicit, since a plain `<button>` doesn't get a pointer cursor by default the way an `<a>` does (`.clickable-icon` sets `cursor: var(--cursor)`, a theme variable, so this stays as a belt-and-suspenders guarantee rather than relying on that resolving to "pointer").

The pin button's `click` listener is a plain, synchronous callback — `() => void this.togglePin(entry, file)` — that delegates to the `private async togglePin()` method rather than passing an `async` function directly to `addEventListener`: the DOM listener type expects a `void` return, not a `Promise`, and an `async` callback there would still run but leave any rejection (if `setPinned()` ever throws) completely unhandled. `togglePin()` updates `entry.pinned` **in place** on the already-rendered `NoteEntry` immediately after the write, rather than re-reading `getFileCache()` or calling `refresh()`: Obsidian's metadataCache re-parses a frontmatter write asynchronously, so a synchronous re-read right after `await setPinned(...)` could still observe the pre-write value. The vault's own subsequent `modify`/`metadataCache "changed"` events (the write does trigger them, same as any other frontmatter edit) still reach `main.ts`'s normal debounced `refresh()` shortly after, so `cachedEntries` catches up regardless — the in-place update is purely to make the *this* click feel instant rather than waiting on that round trip.

That same async-re-parse lag also broke the **content** rendering for the note whose pin was just toggled, in a more visible way: `renderEntry()` used to find where the body starts via `cache?.frontmatterPosition?.end?.offset` — a byte offset from that same stale-for-a-moment cache. `processFrontMatter` had already rewritten the file (e.g. `pinned: true` → `pinned: false`, one byte shorter) by the time the immediately-following `render()` read it, but the cached offset still described the *previous* frontmatter block's length. Slicing the fresh raw content at the stale offset landed a few bytes into the old block, so `body` started with a stray `-` left over from the closing `---` delimiter — which Markdown renders as a bullet list item, for exactly as long as it took the next real `refresh()` (metadataCache event → debounce) to fix the offset. `stripFrontmatter()` fixes this by deriving the cut directly from the raw content just read (a `^---\n(?:.*\n)*?---\n?` regex) instead of trusting any cache — immune to the race by construction, whether or not the edit was ours. The body group matches whole lines lazily (`(?:.*\r?\n)*?`) rather than `[\s\S]*?` specifically so it also matches zero lines: an earlier version used `[\s\S]*?\r?\n---`, which required a newline *before* the closing `---` that's separate from the one ending the opening line — a completely empty frontmatter block (`---\n---\n`, zero properties) has no such extra newline, so that version silently failed to match and left both `---` lines rendering as a stray bullet.

In `render()`, `filteredEntries` (the tag/date/month result) is partitioned into pinned-then-unpinned via two `Array#filter()` passes rather than a fresh sort — `cachedEntries` is already sorted newest-first and `filter()` is stable, so partitioning alone preserves that order within both groups, at the cost of one extra O(n) pass instead of an O(n log n) sort. Pin status only affects this ordering; it plays no part in whether an entry passes the tag/date/month filter in the first place.

### `refresh()` vs `render()` — why there are two

`NotesListView` splits its single old `refresh()` method in two, because the per-note scan (`app.metadataCache.getFileCache(file)`, `resolveDate()`, `getAllTags()` for *every* note in scope) is the one genuinely expensive step once a folder has thousands of notes — measurably slow (multiple seconds) at ~8000 notes, even though each note's individual cost is small:

- `rebuildEntries()` does that scan once and stores the sorted result in `cachedEntries` (a `TFile` reference + resolved date + tags per note — never file content). It also fixes a redundant double `getFileCache()` call an earlier version had (`resolveDate()` now takes the already-fetched `cache` as a parameter instead of re-fetching it).
- `render()` is everything else — filtering `cachedEntries` by the active tag/date/month, paginating, building the heatmap and tag tree, and rendering the DOM. All of that is proportional to *small* bounded quantities (`notesPerPage`, ~26 heatmap weeks, the unique-tag count), not to the total note count, so it's fast regardless of folder size.
- `refresh()` is now just `rebuildEntries()` + `render()` — kept as the public entry point so `main.ts` (vault events, settings changes) and `onOpen()` don't need to change; they still call something that guarantees fresh data.

Every interaction that only changes *view* state — clearing or selecting a tag/day/month filter, expanding/collapsing a tag-tree node, changing page, toggling the `readableLineLength` CSS class — calls `render()` directly instead of `refresh()`. None of those can add, remove, or change the metadata of a note, so re-scanning the whole folder for them would be pure waste. If you add a new interaction, ask whether it can possibly change which notes are in scope or their resolved date/tags: if not, wire it to `render()`, not `refresh()`.

### Pagination

`NotesListView.currentPage` (transient, like `selectedTag`) is clamped into `[1, totalPages]` on every `render()` based on `visibleEntries.length` and `settings.notesPerPage`, then `visibleEntries` is sliced to just that page's window (`pageEntries`) **before** calling `renderEntry()` — the only step that actually reads file content (`vault.cachedRead`) and runs `MarkdownRenderer.render`. This is what keeps a large watched folder fast to page through *within* a single `render()`: the expensive-per-`render()` work scales with `notesPerPage`, not with the total note count (`rebuildEntries()`'s one-time scan, above, is the part that scales with total count). `renderPagination()` renders prev/next buttons only when a previous/next page exists, and windows the page-number buttons to at most 5, sliding to keep `currentPage` inside the window (clamped at both ends so it never shows fewer than 5 when `totalPages >= 5`). Selecting or clearing any of the three filters, and toggling a note's pin (which reorders `visibleEntries`, floating it to/from the top), always resets `currentPage` to 1; other refresh triggers (vault events, settings changes) just re-clamp it, so unrelated background updates don't kick you back to page 1 mid-browsing.

`pageEntries` are rendered by looping and pushing each `renderEntry(mainEl, entry)` call's promise onto an array, then `Promise.all`-ing that array once at the end, rather than a sequential `for...await` loop — safe because `renderEntry()` creates its own `item`/`contentEl` container synchronously before its first `await`, so the loop still appends every entry's container to `mainEl` in page order as it runs; only the async content-fill (the part that actually costs time) runs concurrently instead of one note at a time. Date group headers (below) are inserted into that same loop, synchronously, for the same reason.

### Markdown rendering styles

Each note body's container is `div.notes-list-content.markdown-rendered`. The `markdown-rendered` class is required, not cosmetic: Obsidian's own `app.css` (verified by extracting it from `obsidian.asar`) scopes its table (`.markdown-rendered table`/`th`/`td`), code block (`.markdown-rendered pre`/`code`) and copy-code-button styles under that class. Without it, `MarkdownRenderer.render()`'s output fell back to bare browser styles: unstyled tables, and code blocks without a background plus an always-visible, unstyled copy button. The class's own base rule only sets `tab-size`, so it has no other layout side effects here. Any new element that hosts `MarkdownRenderer` output needs the same class. The body's double-click-to-open handler skips targets inside `a, button`, so double-clicking a code block's copy button doesn't also open the note.

### Markdown rendering lifecycle

`renderEntry()` calls `MarkdownRenderer.render(app, body, contentEl, file.path, component)` — that last argument is a `Component`, used by Obsidian to scope whatever the renderer itself registers (event listeners, etc. for the rendered content) so it can be torn down later. It's `this.markdownComponent`, a `Component` the view owns itself — **not** `this.plugin` (an earlier version passed the plugin instance here, flagged by a community plugin review: the plugin's lifecycle spans the entire Obsidian session, so anything registered against it as a "component" would never get cleaned up until the plugin unloads, no matter how many times this note's content gets re-rendered). Since `render()` fully rebuilds the DOM from scratch on every call (see above) but never previously tore down whatever a *previous* pass's `MarkdownRenderer.render()` calls had registered, `render()` now starts by unloading the current `markdownComponent` and replacing it with a fresh one, before any `renderEntry()` calls happen — so each pass's registrations are scoped to *that* pass, not accumulated indefinitely across every re-render for as long as the view stays open. `onClose()` unloads it one final time when the view itself closes.

### Date group headers

`settings.showDateGroups` (default off) shows a `.notes-list-date-group-header` label — "Today", "Yesterday", "This week", or "Older" — above the list wherever consecutive `pageEntries` cross into a new group, via `dateGroupLabel(date)`: today and later folds into "Today" (a future-dated note has no label of its own to fit, and "today or later" avoids inventing a fifth one), exactly yesterday is "Yesterday", on/after `moment().startOf("week")` (locale-aware, same convention `heatmap.ts` uses for its own week columns) is "This week", everything else is "Older". This is computed **per page**, not once over all of `visibleEntries` before slicing — pagination still only depends on `notesPerPage`/`currentPage` (see "Pagination" above), and a group that happens to span a page boundary just shows its header again at the top of the next page rather than the view tracking which group was last shown on the previous one.

Pinned entries are skipped entirely by this loop — no header is shown for one, and it doesn't update `lastGroup` either. Pinned notes already float to their own spot at the top of `visibleEntries` regardless of date (see "Pinned notes" above), so grouping them in with the date-based headers would either show a header out of chronological order (an old pinned note landing ahead of a "Today" note) or make the first *unpinned* entry wrongly skip re-showing a header that only appeared above the pinned block.

### Readable line length

`internalVault(app).getConfig("readableLineLength")` / `.on("config-changed", ...)` — an undocumented internal Vault surface — reads and watches Obsidian's editor-wide "Readable line length" setting, so the notes column's `is-readable-line-width` class (and thus its `max-width: var(--file-line-width)`) mirrors the same core mechanism used by `.markdown-preview-view.is-readable-line-width` (confirmed by inspecting the app's own `app.css`/`app.js`).

### Layout

`.notes-list-view` (the `ItemView`'s `contentEl`) is the single scroll container (`overflow-y: auto`, no padding of its own), so the browser's scrollbar sits at the pane's real right edge, same as any other Obsidian view. The visual inset (`padding: var(--size-4-4)`) lives one level in, on `.notes-list-layout` (the flex row: `.notes-list-main`, flex-grow, and `.notes-list-heatmap-panel`, `flex: 0 0 auto`, sized to its own content and never shrinking).

The heatmap panel is `position: sticky` with `top: var(--size-4-4)` — matching `.notes-list-layout`'s padding-top exactly, since the panel already sits that far from the scroll container's top before any scrolling happens; if `top` didn't match, the panel would visibly slide up by the difference before locking in place on the first scroll. This keeps the heatmap pinned and fully visible while the notes list scrolls past beside it.

### Heatmap edge-cell clipping

`.notes-heatmap-scroller` sets `overflow-x: auto` for horizontal scrolling of the grid — but per the CSS overflow spec, setting only one axis to a non-`visible` value implicitly computes the other axis (`overflow-y`, left unset) to `auto` as well, so it clips in *both* directions. Selected day cells and month labels are highlighted with `outline`, which paints outside the element's box; without padding on the scroller, cells flush against its edge (first/last week column, top/bottom row) had their outline clipped by that implicit clipping box. `.notes-heatmap-scroller` carries a small `padding: 3px` on every side specifically to leave room for that outline; `padding-bottom` is then further increased (`calc(3px + var(--size-2-2))`) beyond that shared 3px, purely for visual spacing before the `.notes-heatmap-legend` row that follows the scroller as its next sibling — removing the base 3px (on any side) reintroduces the clipping, independent of that extra bottom spacing.

### Text selection

Obsidian sets `body { user-select: none }` globally (confirmed in the app's own `app.css`) and only re-enables it on its own reading/editing views and `[contenteditable]` elements — a custom `ItemView` like this one isn't covered by that allowlist by default. `.notes-list-item` opts back into `user-select: text` explicitly for that reason. Any new custom sub-view added here that should have selectable text needs the same opt-in.

### Known limitations (identified, not fixed)

These were found during a review of the codebase looking for bugs from past reworks, and are deliberately left as-is rather than patched — either because a correct general fix isn't possible/simple, or because fixing them is a design decision rather than a clear-cut bug:

- **A single note edit still triggers a full `rebuildEntries()` rescan** of every note in scope (debounced, via `onVaultEvent()` → `requestRefresh()`), not just the one file that changed — there's no per-file cache patching. Fine at the folder sizes this has been tested at (thousands of notes debounced together), but a genuinely incremental update would need a larger redesign of `cachedEntries` than a quick fix. Left as-is for now.
