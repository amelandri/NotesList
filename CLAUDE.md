# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Obsidian community plugin ("Notes List", id `notes-list`) that opens a custom two-column view: a chronological list of notes from one configurable vault folder on the left, and a GitHub-style contribution heatmap of note activity on the right.

## Commands

- `npm run build` — type-check (`tsc -noEmit -skipLibCheck`), lint (`eslint . --max-warnings 0`; see "Lint" below), then bundle `src/main.ts` → `main.js` via esbuild (production, no sourcemap).
- `npm run dev` — esbuild in watch mode (inline sourcemap), no type-check.
- `npm run install-to-vault` — copies `manifest.json`, `main.js`, `styles.css` into `<vault>/.obsidian/plugins/notes-list/`. The target vault is the `DEFAULT_VAULT` in `copy-to-vault.mjs`, overridable with `OBSIDIAN_VAULT_PATH`. **`copy-to-vault.mjs` is local only**: untracked and listed in `.gitignore`, because it holds the user's own vault path and the repository is public, so a fresh clone has no deploy script until one is created. Never re-add it to git, and don't write vault paths into this file either. The target is a real, in-use vault, so the copy only ever overwrites those three files, never its `data.json`.
- `npm run deploy` — `build` + `install-to-vault`; the normal edit/verify loop for this repo. After deploying, reload Obsidian (`Cmd+R`) to pick up the new `main.js`/`styles.css` — `npm test` (below) covers the plugin's pure logic, but nothing exercises the actual Obsidian integration or rendered DOM, so this manual reload against the live vault is still the only way to verify those.
- `npm run release -- <x.y.z>` (`release.mjs`) — from a clean, up-to-date `dev`: bumps `manifest.json`/`package.json`/`versions.json`, moves `CHANGELOG.md`'s `## [Unreleased]` entries under a new `## [x.y.z] - YYYY-MM-DD` heading (and updates the compare links at the bottom), builds, commits "Bump version to x.y.z", tags, pushes `dev` and the tag together (`--atomic`), fast-forwards `main` (never forced), and publishes a GitHub release with `main.js`/`manifest.json`/`styles.css` attached. The release notes are that version's changelog entries, plus the definitions of any reference-style links they use (e.g. `[#1]`, which would otherwise not resolve outside the changelog) and a "Full changelog" compare link. **Re-runnable with the same version** after a failure partway through: if HEAD is already that bump commit (and the tag, if present, points at it), it skips the bump/commit/tag and continues with the remaining steps. Pushes are no-ops when already done, and an existing GitHub release is reused, with its notes re-read from the committed changelog and its assets replaced by a fresh build. Pushes retry up to 3 times, 5s apart, because GitHub has been seen rejecting a valid tag push with a bare `! [remote rejected] <tag> (failed)` that succeeded on a plain retry. It refuses to continue if the tag exists but points somewhere other than HEAD. Resuming needs HEAD to still be the bump commit, so don't commit anything else in between; a fix to the script itself has to be run from an uncommitted copy until the release is done.
  `CHANGELOG.md` uses the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format: add entries under `## [Unreleased]` as changes land (user-facing changes only; internal refactors and dev tooling stay out). The script refuses to release if that section is empty, before modifying anything, and it takes no release-notes argument: the changelog is the single source. After a release, "Unreleased" holds only the placeholder line `_No unreleased changes yet._` (`UNRELEASED_PLACEHOLDER` in `release.mjs`), so the section never reads as accidentally blank. Replace it with the first new entry; if it's left in by mistake, the release strips it anyway and never counts it as a change, so the placeholder alone still means "nothing to release".
- `npm run lint` — just the lint step on its own.
- `npm test` — runs the automated test suite (`vitest run`) under `test/`. See "Automated tests" below for what is and isn't covered and why.
- `npm run generate-test-notes -- [count] [folder]` (or `node generate-test-notes.mjs [count] [folder]`) — writes `count` (default 100) throwaway `.md` notes into `<vault>/[folder]` (default `Note`) for load-testing the list/heatmap/tag-tree against a large folder. Same identical multi-paragraph Lorem ipsum body every time (content doesn't affect what's being measured — edit the `BODY` array directly to change its length/shape); `timestamp` frontmatter randomized across the last 6 months; 0–3 random `tags` per note (frontmatter list) drawn from `TAG_POOL`, nested up to 4 levels, with parents also used on their own and one casing-only variant (`Reading` vs `reading/books`) to exercise the tag tree's case-insensitive merge; filenames follow the `YYYYMMDDHHmmss` pattern (deduped with a `-2`, `-3`, … suffix on collision), matching this plugin's own default `uniqueNoteNameFormat` (see "Self-contained note creation" below). Dev-only, not part of the shipped plugin — same `OBSIDIAN_VAULT_PATH` override as `copy-to-vault.mjs`, but its own `DEFAULT_VAULT` is a separate, throwaway test vault, deliberately *not* the deploy one, so generated notes never land in the real vault by accident.

`npm test` (`vitest run`) runs the automated test suite under `test/` — see "Automated tests" below. `esbuild.config.mjs` marks Node builtins as external to esbuild's bundling via `node:module`'s own `builtinModules` (not the separate `builtin-modules` npm package, which this project used to depend on — Node has exposed the same list natively since well before this project's minimum supported Node version, so the extra package was redundant; a community plugin review flagged it, per the [module-replacements](https://github.com/es-tooling/module-replacements) project). Before cutting a release, verify `package-lock.json` is actually installable with `npm ci` (not just `npm install` — `ci` additionally fails on a lockfile that's drifted from what the registry can still resolve, which `install` alone can silently tolerate by rewriting the lockfile); a stale entry pinning a since-removed transitive dependency version is exactly what broke the automated review's own dependency install once, and `npm install` alone didn't surface it.

### Lint — keeping the community plugin review's warnings from coming back

`eslint.config.mjs` runs `eslint-plugin-obsidianmd`'s `recommended` config, the Obsidian team's own rule set that the community plugin review uses (ESLint core, typescript-eslint type-checked rules, and Obsidian-specific rules such as `obsidianmd/ui/sentence-case` and `depend/ban-dependencies`). It runs on `src/` and `package.json`; dev scripts (`*.mjs`), `test/` and `main.js` are ignored. It's part of `npm run build`, so `deploy` and `release` can't skip it. `--max-warnings 0` makes warnings fail the build too, because the review reports warnings and the sentence-case rule, for one, is only a warning. Fix what it reports rather than configuring it away: an exception here (e.g. the sentence-case rule's `brands` option) wouldn't apply in the review, which runs the defaults. That's why the ribbon tooltip is "Open notes list", not "Open Notes List".

The official config alone doesn't reproduce two ways this project has passed lint locally but failed in the review, because both depend on the review's environment resolving fewer types than a local install. Two extra guards cover them:

- **Newer built-ins** (`String.prototype.trimEnd`, ES2019, was the real case): locally `@types/node` quietly declared them, so `tsc` passed even though `lib` didn't include them; in the review they typed as `error` and tripped `no-unsafe-call`. `tsconfig.json` now sets `"types": []`, so no `@types/*` package is pulled in implicitly and `tsc` itself fails on any built-in `lib` doesn't cover (`lib` includes `"ES2019"` for `trimEnd`). Add the matching `lib` entry when `tsc` reports a "does not exist on type … try changing the 'lib' compiler option" error; it's type-only, and Obsidian's Electron/mobile engines support these natively. (`src/` needs no Node types: it runs in Obsidian's renderer, and DOM covers timers etc.)
- **`moment`**: see the `src/moment.ts` note below. A `no-restricted-imports` rule fails lint on importing `moment` from `"obsidian"`, or from the `moment` package itself, anywhere in `src/` except `src/moment.ts`.

Each guard was verified by reintroducing its original error in a scratch copy and confirming `npm run build` fails: `moment` imported from `"obsidian"`, an ES2021 built-in (`replaceAll`), an untyped `processFrontMatter` callback, an unnecessary `as` assertion, a Title Case UI string, and `moment` re-added as a dependency. The clean tree builds with zero problems.


**`src/moment.ts` — why no source file imports `moment` from `"obsidian"` directly.** `obsidian.d.ts` types its `moment` export via `import * as Moment from 'moment'`, and the community plugin review's lint environment can't resolve that import. `moment` then types as `error`/`any` there, and every `moment()`-derived value trips the whole `@typescript-eslint/no-unsafe-*` family (`-assignment`, `-call`, `-member-access`, `-argument`, `-return`: dozens of hits across `heatmap.ts`/`main.ts`/`view.ts`). Declaring `moment` as a devDependency was tried first and did **not** fix it in the review. `src/moment.ts` therefore declares its own minimal `Moment` interface (only the methods this plugin actually calls) and re-exports Obsidian's `moment` cast to it (`as unknown as MomentFactory`), so type checking no longer depends on the `moment` package's typings resolving at all. Runtime is unchanged: it's still Obsidian's own bundled moment instance. Everything in `src/` imports `Moment`/`moment` from `./moment`. To call a moment method not yet declared there, add it to the interface first, matching moment's real signature. This was verified locally with typed ESLint (`recommendedTypeChecked`) in three setups: `moment` resolving normally, `moment` missing (`error` type), and `moment` stubbed as `any`. The old code reproduced every warning family in the `any` setup; the new code is clean in all three. `moment` is deliberately **not** a direct dependency: it was briefly added as a devDependency, which didn't fix the review and is itself flagged by `depend/ban-dependencies`. `test/obsidian-mock.ts` and the tests still import the real package, which is installed transitively as a dependency of `obsidian`.

## Architecture

- `src/main.ts` — `Plugin` entry point. Registers the `ItemView`, a ribbon icon + command to open it (`id: "open"`, `name: "Open"`), a second command to create a new note (`id: "create-new-note"`, `name: "Create new note"` — see "Self-contained note creation" below — deliberately no default hotkey, per Obsidian's own plugin guidelines; the user assigns one from Settings → Hotkeys), a third to open the view with its search field focused (`id: "search-notes"`, `name: "Search notes"`, also no default hotkey; see "Full-text search" below), and the `PluginSettingTab`. Neither command's `id`/`name` repeats the plugin's own id (`notes-list`) or name (`Notes List`) — Obsidian already prefixes every command with the plugin name in the command palette (`"Notes List: Open"`) and namespaces ids internally, so doing it again here is redundant and is flagged by the community plugin review as such (an earlier version had `id: "open-notes-list"`, `name: "Open Notes List"`). Also wires vault (`modify`/`create`/`delete`/`rename`) and `metadataCache` (`changed`) events to a debounced `requestRefresh()` that re-renders any open `NotesListView` leaf. `onVaultEvent(file, oldPath?)` first checks `isInScope()`, which mirrors `NotesListView.getNotesInScope()`'s own folder/subfolder logic exactly (not a bare `path.startsWith(folderPath)`, which would also match e.g. `NotesArchive/x.md` against a `Notes` folder setting) — for `"rename"` specifically, both the new `file.path` **and** the passed `oldPath` are checked, since a note renamed/moved *out* of the watched folder only has its new (now out-of-scope) path by the time the handler runs, and checking only that would leave the stale entry showing until an unrelated event happened to trigger a refresh. Settings persist via `loadData`/`saveData` (`data.json` in the plugin folder), merged over `DEFAULT_SETTINGS` — but only *after* `loadSettings()` first runs the raw loaded data through `migrateSettings()` (see "Settings migrations" below), so `Object.assign` always merges an already-current shape. `loadSettings()` also runs `settings.folderPath` and `settings.templatePath` through the module-level `normalizeOptionalPath()` (Obsidian's own `normalizePath()`, with `""` special-cased ahead of it since `normalizePath("")` returns `"/"`, which would break the `""` = "entire vault"/"no template" sentinel both settings rely on) — both on every load (so a value saved before this normalization existed still gets cleaned up) and again in each setting's own `onChange`. Because of that, `isInScope()` and `getNotesInScope()` (in `view.ts`) both read `settings.folderPath` directly with no further trimming; the old inline `.replace(/^\/+|\/+$/g, "")` duplicated in both places is gone. There's deliberately no `onunload()` override: Obsidian's own plugin guidelines call out detaching a plugin's leaves there specifically, since the same `onunload` path also runs on a plugin *update* (not just a manual disable) — detaching would close the user's open Notes List tab on every update instead of letting it quietly reinitialize once the plugin reloads.
- `src/settings.ts` — the `NotesListSettings` shape and defaults: `folderPath`, `includeSubfolders`, `contentDisplay` (`ContentDisplayMode`: `"full" | "preview"`), `previewLength`, `notesPerPage`, `showNoteName` (`ShowNoteNameMode`: `"never" | "always" | "whenDifferent"`), `showDateGroups`, `uniqueNoteNameFormat` (a moment.js format string), `templatePath` (empty = no template; see "Self-contained note creation" below), `tagTreeExpandLevel` (`TagTreeExpandLevel`: `"1" | "2" | "3" | "all"`; see "Tag tree expansion" below), plus a `mobile*` twin of each "Notes list"/"Sidebar" field (see "Device-specific settings" below). Pin state is *not* here — see "Pinned notes" below.
- `src/view.ts` — the `ItemView` (`VIEW_TYPE_NOTES_LIST`). `refresh()` (rescans every note in scope, expensive) and `render()` (rebuilds the DOM from scratch — `contentEl.empty()` then re-render, rather than diffing — from the already-scanned `cachedEntries`, cheap) are separate for performance at scale; see "`refresh()` vs `render()`" below.
- `src/moment.ts` — locally-typed re-export of Obsidian's `moment` (see the note under Commands for why).
- `src/searchIndex.ts` — the full-text search index (`SearchIndex`) and its pure query helpers; see "Full-text search" below.
- `src/heatmap.ts` — pure DOM-rendering function `renderHeatmap(container, dates, selection)`, no plugin/view state (`selection: HeatmapSelection` bundles `selectedDate`/`onSelectDate`/`selectedMonth`/`onSelectMonth` — grouped into one object once the parameter list grew past a couple of callbacks). Buckets note counts per day into a 6-month, GitHub-style week/weekday grid; every real (non-future) day cell gets a tooltip and a click handler calling `onSelectDate` with its `"YYYY-MM-DD"` key (`.is-selected` when it matches `selectedDate`), and the (one per month) visible month label gets a click handler calling `onSelectMonth` with its `"YYYY-MM"` key (`.is-selected`/`.is-clickable` likewise). A label sits on its month's first week column and overflows to the right until the next one, so a month with a single column of room (the window's partial first month, or the current month just after it starts) would overlap the next label: `monthSpans()` counts each column's remaining run in its month, and `monthLabelText()` shrinks a span-1 label to its capitalized initial plus a period ("S."), and always upper-cases the first letter otherwise too, since some locales' short month names are lower case (Italian "giu"), with the full "MMMM YYYY" in every label's `title`. Both are pure and tested. The empty labels after a month's first column come later in the DOM and so sit on top of its overflowing name: they're `pointer-events: none` (`:not(.is-clickable)`), otherwise only the name's first 10px would take clicks. The labels also carry bottom padding, in place of the row's old `margin-bottom`, for a taller click target. The legend row ends with `.notes-heatmap-total`, pushed to the row's right edge with `margin-left: auto` since `.notes-heatmap-legend` is a flex row. `renderHeatmap`'s new `visibleCount` parameter (the caller's already-filtered count, e.g. `visibleEntries.length` in `view.ts`) is compared against `dates.length` (every note in scope, unfiltered, not just the ones inside the 6-month window): equal → just the total; otherwise → `"{visibleCount} of {total} notes"`. No separate "is a filter active" flag is threaded through — the two counts simply differing is what drives the "of" format, so it stays correct by construction even if a new filter kind is added later. `maxCount` (the color-scale divisor for `levelFor()`) is computed only from days actually drawn in the visible `start..today` window, not from every entry in `dayCounts` — `dates` includes every note in scope regardless of age, so a single outlier day outside the 6-month window (e.g. a bulk import) would otherwise dominate `maxCount` and flatten every visible cell's contrast down near "Less" even on the grid's own busiest day.
- `src/tagTree.ts` — pure functions for the tag browser: `buildTagTree(perNoteTags)` takes **one tag array per note** (not a pre-flattened list — see "Tag note counts" below) and groups `#a/b/c`-style tags (as returned by `getAllTags`) into a nested `TagTreeNode` map by splitting on `/`, each node also carrying a `count`; `renderTagTree(container, root, selectedPath, isCollapsed, onSelect, onSetCollapsed)` renders it as nested, collapsible `<ul>`s (`isCollapsed(path, depth)` decides each node's state, see "Tag tree expansion" below) (a chevron toggle appears only on nodes with children), each label suffixed with `(count)`; `tagMatchesFilter(tag, filter)` implements Obsidian's usual hierarchical tag semantics (selecting a tag also matches its sub-tags), matching **case-insensitively** to mirror Obsidian's own tag pane, which treats `#Project` and `#project` as the same tag. That merge happens in two places: `getOrCreateChild()` keys `TagTreeNode.children` by the segment's lowercased form (whichever casing is seen *first* wins for that node's displayed `segment` and its `path`, which doubles as the filter value passed to `tagMatchesFilter`), and `buildTagTree()`'s per-note `reachedPaths` is keyed by lowercased path too, so a single note carrying both `#Project` and `#project` still only increments that node's count once, not twice.
- `src/tasks.ts` — pure task counting and filtering for the sidebar's Tasks section; see "Tasks" below.
- `src/openTasks.ts` — pure grouping of open tasks by tag combination for the open-tasks mode; see "Open tasks view" below.
- `src/i18n.ts` — every UI string, per language (English and Italian), with `t()`/`tn()`; see "Localization" below.
- `styles.css` — all view styling, loaded automatically by Obsidian alongside `main.js`/`manifest.json`.

### Localization

**No user-visible string is written inline**: every one is a key in `src/i18n.ts`, read through `t(key, vars)` or, for counts, `tn(key, count, vars)`. That covers command and ribbon names, view labels, `aria-label`s, placeholders, notices, settings names, descriptions and dropdown options, date group labels, heatmap legend and tooltips, and the tag/task entries. The English table `en` is the complete base and defines the keys (`MessageKey`). Every other table is typed `Translations`, so `tsc` rejects a missing or extra key, and `test/i18n.test.ts` also checks that each translation uses the same `{placeholders}` as English. Plural entries hold one form per `Intl.PluralRules` category (`one`, `other`, …; `other` required and used as the fallback), so plural rules come from the browser, not from `count === 1`. The language is Obsidian's `getLanguage()` (public API since 1.8.7, under the 1.13.0 `minAppVersion`), read once on first use since changing it needs an app restart anyway; a regional code falls back to its base language (`it-CH` → `it`), then to English. `setLanguage()` exists for tests only, and the mock's `getLanguage()` returns `"en"`.

Rules that keep strings translatable: put **whole sentences** in the tables, never fragments joined in code, since word order and agreement differ. That's why the empty-list message is one template ("No notes match: {filters}.") listing the same labels as the filter pills (both from `activeFilters()`), and why the per-device settings note has a full desktop and a full mobile variant. Also don't transform a translated string in code (the old "Tasks: " + lowercased label pill became its own `tasks.pill.*` keys). Key names built in code are typed with `as const` template literals (`` `tasks.pill.${filter}` ``), so `tsc` still checks them. Dates already localize themselves: moment follows Obsidian's locale for month names, `D MMM YYYY`/`MMMM YYYY`, and the first day of the week. The note date link deliberately stays ISO-like (`YYYY-MM-DD HH:mm`). The CSS uses logical properties (`margin-inline-start`, `padding-inline-start`) where it used to say left, so right-to-left languages mirror correctly.

The `obsidianmd/ui/sentence-case` lint rule checks string literals at UI call sites, and those are now `t()` calls, so it no longer sees the texts: **keep the tables in sentence case by hand**, in every language. To add a language: add a `Translations` table, register it in `TRANSLATIONS`, and run the tests.

### Automated tests

`test/*.test.ts` (Vitest, `npm test`) cover this plugin's pure logic — parsing, matching, counting, migrating — directly, with no Obsidian instance and no DOM. What they deliberately **don't** cover: `NotesListView.render()`/`renderEntry()`, the settings tab's rendering (Obsidian draws it from `getSettingDefinitions()`; `validatePositiveInteger()` is the one testable piece), `createUniqueNote()`'s actual vault/frontmatter/API calls, or anything else that genuinely needs a live Obsidian environment — that's still what the manual `npm run deploy` + reload loop is for (see Commands above).

The real `obsidian` npm package ships **no runtime at all** — `node_modules/obsidian/package.json`'s `"main"` is empty; it's type declarations only, resolved by the real app at plugin load time. Importing a `src/*.ts` file that does `import { ... } from "obsidian"` would crash immediately in a plain Node test process for want of anything to import. `test/obsidian-mock.ts` stands in for it, wired up via `vitest.config.ts`'s `resolve.alias` (test-only — `esbuild.config.mjs` still marks `"obsidian"` external for the actual plugin build, completely unaffected by any of this). It re-exports the *real* `moment` package (already a genuine transitive dependency of `obsidian` itself, and this project's date logic depends on its exact behavior — a fake would defeat the point of testing it), and otherwise provides bare, no-behavior stubs (`ItemView`, `Plugin`, `TFile`, `Notice`, etc.) — just enough that a module *imports* without throwing; nothing in the mock is meant to emulate Obsidian's real UI/vault behavior, so no test relies on it doing anything beyond existing.

A handful of functions were hoisted out of `NotesListView`/`NotesListPlugin` methods into plain module-level `export`ed functions specifically so tests could call them directly, without constructing a (heavily mocked) view/plugin instance first — in every case this was a *pure, behavior-preserving* move, not a redesign: each one was already private and didn't reference `this` at all (`parseDatetime()` and `dateGroupLabel()`, both formerly on `NotesListView`; `resolveUniqueNoteNameFormat()`, extracted from the one line of logic inside `NotesListPlugin.uniqueNoteNameFormat()` that doesn't touch `this.settings` beyond its own parameter). `dateGroupLabel()` also gained a `now: moment.Moment = moment()` parameter (defaulting to the real current time for every existing call site, so production behavior is unchanged) purely so tests can pin "today" to a fixed instant instead of a result that depends on which real day the suite happens to run on. `heatmap.ts`'s day-bucketing and window-scoped max-count logic (`countByDay()`, `computeVisibleMaxCount()`) and `levelFor()` were similarly split out of `renderHeatmap()`'s body into their own exported functions — `renderHeatmap()` itself still isn't tested directly (it's pure DOM construction), but the color-scale math that was the actual source of a real bug this session (an outlier day outside the visible window skewing every visible cell's contrast) now is.

### Note dating convention

A note's date/time comes from its **frontmatter**: `resolveDate()` in `view.ts` reads a single `timestamp` property via `metadataCache.getFileCache(file)?.frontmatter`, meant to be set through Obsidian's own **"Date & time"** property type (Properties panel → type dropdown), not typed by hand. This replaced an earlier two-field `date`/`time` convention — see "Legacy `date` fallback" below for what still reads from old notes. It's deliberately *not* called `datetime` — that's Obsidian's own fixed internal name for the property *type* itself (see "Self-contained note creation" below), and naming the property the same thing made error messages read like a tautology ("the `datetime` property must be of type datetime").

Obsidian's own property picker, verified directly by extracting `obsidian.asar` from a real install (`/Applications/Obsidian.app/Contents/Resources/obsidian.asar`, **not** the tiny launcher `app.asar` next to it) and reading its actual formatting code, always writes this value as a **quoted string in local wall-clock time**: `"YYYY-MM-DDTHH:mm:ss"` (its date-only "Date" property type writes the same way, just `"YYYY-MM-DD"`). Concretely: `AA(date)` formats the date part via `date.getFullYear()`/`getMonth()`/`getDate()` (all local accessors, confirmed by grepping the bundle — it contains zero calls to any `getUTC*` accessor), `PA(date)` formats `HH:mm:ss` the same way, and the picker's own `toString()` is `time ? AA(date)+"T"+PA(date) : AA(date)`. That result is a plain JS string, and reproducing Obsidian's own frontmatter write with the `yaml` npm package (`YAML.stringify({ timestamp: "2026-09-25T16:20:00" }, { schema: "yaml-1.1" })`) confirms the library quotes it automatically — because *unquoted*, YAML 1.1 would resolve that same text as a timestamp. So the property picker's output is immune to every quirk below by construction: no auto-cast, no UTC conversion, nothing to defend against.

`parseDatetime()` handles the value defensively anyway, for a value typed by hand straight into the raw YAML (bypassing the property picker and its quoting):

- **String** (the normal case): parsed strictly against `["YYYY-MM-DDTHH:mm:ss", "YYYY-MM-DDTHH:mm", "YYYY-MM-DD"]` — local time, at face value, no conversion.
- **Neither a string nor a `Date`** (a YAML number, a list, …): rejected outright (`null`, so `resolveDate()` falls through to its next fallback) via an explicit `raw instanceof Date` check — not handed to `moment()`, which would e.g. read a bare number as epoch milliseconds. That check is also what lets `moment(raw)` be called without an `as moment.MomentInput` assertion on an `unknown` value, which the community plugin review flagged as unnecessary (in its environment `moment` resolved as `any`; see the `src/moment.ts` note under Commands).
- **A native JS `Date`** (from an *unquoted* value — YAML 1.1's timestamp resolver auto-casts it, same mechanism this section used to document at length for the old `date`/`time` fields): a bare, time-less `timestamp: 2026-09-25` always resolves to *exactly* UTC midnight, with no exceptions (`Date.UTC(year, month, day)` — hour/minute/second default to `0` whenever the source text carries no time-of-day at all), so `parseDatetime()` forces `.startOf("day")` (local midnight) only when `date.clone().utc().format("HH:mm:ss") === "00:00:00"` — converting that instant to local time for display would otherwise print a spurious non-midnight local hour (e.g. 01:00/02:00) purely as a timezone artifact. Checking the *UTC* time-of-day, not the local one, is what tells that apart from a genuinely combined, unquoted `timestamp: 2026-09-25 16:20:00` (also accepted by the same resolver, with a real, non-midnight time-of-day baked in) instead of stomping on it too. **Residual limitation**: that unquoted-combined case is still interpreted as UTC, not local (the resolver has no notion of "local time"), so its time-of-day comes out shifted by whatever the runtime's UTC offset is — typing it unquoted is what causes this; the property picker's own quoted output never hits this path at all.

If `timestamp` is missing, or doesn't parse, `resolveDate()` falls back to `file.stat.mtime` (last-modified time, not creation time — an edit with no explicit `timestamp` set will keep shifting the note's position in the list and its heatmap day). The heatmap consumes the same resolved dates, so it always agrees with the list's ordering. Note this is unrelated to the filename format a newly created note gets (see "Self-contained note creation" below) — that's only about note *creation*, not dating.

#### Legacy `date` fallback

Before `timestamp`, this plugin read two separate frontmatter properties, `date` and `time`. That's gone — `time` is no longer read at all — but `resolveDate()` still falls back to a plain `date` property (via the same `parseDatetime()`, so it's read as a **date only**, never combined with any leftover `time` value) when `timestamp` isn't set, so existing notes written under the old convention don't silently lose their date entirely and fall all the way through to `file.stat.mtime`. There's no equivalent fallback for the old `time` field — a note relying on it shows at local midnight until it's updated to use `timestamp` instead (via Obsidian's own Properties panel, ideally, so it's written correctly-quoted).

`generate-test-notes.mjs` (see Commands above) writes the new `timestamp` convention, quoted, matching Obsidian's own picker exactly (`formatFrontmatterTimestamp()`) — it no longer generates the old two-field shape.

### Content display

`previewBody(body, frontmatterMode, settingMode, previewLength)` (pure, tested) decides what a note's body shows, by precedence:

1. The note's own `content-display` frontmatter (`contentDisplayOverride(fm)`, only exactly `"full"`/`"preview"` count): `"full"` shows everything; `"preview"` cuts at the preview marker, or at `previewLength` when there's none.
2. A **preview marker**, `<!-- more -->` (`PREVIEW_MARKER`, case-insensitive, flexible spacing, WordPress/Hugo convention): cut there regardless of the setting, and regardless of `previewLength`. It's a per-note choice like the frontmatter, so it outranks the global setting.
3. The device's Content display setting, truncating to `previewLength` for `"preview"`.

The marker is an HTML comment on purpose: Obsidian's reading view doesn't show it, and it can't collide with existing content. The user's first idea, a `-----` line, was dropped because it's already valid Markdown (a horizontal rule, or a setext H2 underline right under text), so any note using it as a separator would have been cut. `cutAtPreviewMarker()` finds the first marker outside fenced code blocks (it may be mid-line) and cuts there. In `"full"` the marker is left in the body, where it renders as nothing. There's no magic-number sentinel (no `0` meaning "full"); the mode and the length are separate settings.

The cut itself is `truncateMarkdown(body, previewLength)`, not a bare `slice()`: it never cuts through a fenced code block (```` ``` ````/`~~~`) or a GFM table, since either renders broken when truncated partway (an unclosed fence swallows the rest of the preview as code; a table loses rows mid-way). `findUnbreakableBlocks()` scans the body line by line and returns each such block's `[start, end)` range. A fence closes only on the same character repeated at least as many times, and an unclosed fence runs to the end of the body, as Obsidian renders it. A table is a line containing `|` followed by a delimiter row that also contains a pipe, so a bare `---` setext underline or thematic break isn't mistaken for one. The table then extends until a blank line or a line with no `|`. Because the scan is sequential, a table-looking block inside a code fence counts only as code. If `previewLength` lands strictly inside a block, the cut moves to that block's end, so a preview can run longer than `previewLength` by up to one block; if the block is the last thing in the body, the whole body is returned, not truncated. Both functions are covered in `test/view.test.ts`.

**Showing the cut.** All three functions return a `Preview`, `{ text, truncated }`, rather than a string with a "…" appended. A "Continue reading →" link (`.notes-list-read-more`, `t("view.readMore")`, same `openNote()`) follows in a slot created before `renderEntry()`'s first `await`, so it stays between the content and the tags. The user asked for a more evident cut than the old "…", which was easy to miss (a fade-out of the last lines was tried too, and dropped at the user's request), and which for block cuts sat on its own paragraph because appended to a closing fence or a table row it would have broken them. An inline "…" remains only where a sentence breaks off mid-line (a length cut outside any block, or a mid-line marker).

**Tags are shown extracted, not inline.** A note's tags can come from the frontmatter `tags` property or from `#tags` in the body; `NoteEntry.tags` already has both (`getAllTags()`). `renderEntry()` shows them, deduplicated case-insensitively by `uniqueTags()`, as `a.tag` pills (Obsidian's own tag class) in `.notes-list-tags` below the content; clicking one sets `selectedTag` like the tag tree. The row is created before `renderEntry()`'s first `await`, so it stays after the content. The body itself goes through `stripInlineTags()` before truncation (so `previewLength` counts text, not tags), so inline tags aren't also rendered as text. It mirrors Obsidian's tag rules with a regex (`INLINE_TAG`: `#` at line start or after whitespace, `[\p{L}\p{N}_\-/]`, at least one non-digit), skips fenced code blocks and inline code spans, collapses the spaces a removed tag leaves (keeping the original line's indentation), and drops lines that held only tags. It's regex-based rather than using `metadataCache`'s tag positions on purpose: those offsets go stale right after a frontmatter write, the same race `stripFrontmatter()` avoids (see "Pinned notes"). `String.prototype.matchAll` is why `tsconfig.json`'s `lib` includes `ES2020.String`. Both functions are tested in `test/view.test.ts`.

Double-clicking anywhere in `.notes-list-content`, or on the file name (`.notes-list-title`, when shown; plain text, so no exception needed), opens the note, same as clicking the date link (`openNote()`, a closure shared by all three so they can't drift apart) — except when the double-click lands on an `<a>` or `<button>` inside the rendered body (`evt.target.closest("a, button")`), since the note can itself contain internal/external links, or a code block's copy button, that already handle their own click, and a double-click landing on one would otherwise also fire this handler on top of whatever the link itself does.

### Settings migrations

`migrateSettings(data)` (`settings.ts`) mutates the raw object `loadData()` returns — whatever shape it happens to be, which for an old enough `data.json` may include fields no longer in `NotesListSettings` at all — up to the current shape, in place, before `main.ts`'s `loadSettings()` ever merges it over `DEFAULT_SETTINGS`. `SETTINGS_MIGRATIONS` is an array of one function per past shape change, each one assigned to the settings version it migrates *from* by its position in the array (index `0` migrates a file with no `settingsVersion` field at all — i.e. every file saved before this framework existed — from version 0 to 1, and so on); `migrateSettings()` runs every migration from the file's own saved version (defaulting to `0` when the field is missing) up through the array's end, so a very old file runs all of them in sequence and a current file runs none. The current version is simply `SETTINGS_MIGRATIONS.length` — `DEFAULT_SETTINGS.settingsVersion` reads it directly, so there's nothing to keep in sync by hand when a new migration is appended.

The first entry replays a change already made once, by hand, earlier in this project: an old `contentPreviewChars` number (`0` meant "show full content"; anything higher meant "preview", truncated to that many characters) was split into today's `contentDisplay`/`previewLength`. No real user's `data.json` was ever affected by that specific rename (nobody outside this one dev vault ever ran the version that had it, and this vault's copy was fixed by hand at the time) — the migration exists so the *pattern* is established before this plugin has real users, not to repair that particular file. `loadSettings()` persists the migrated result immediately (`migrateSettings()`'s return value says whether anything actually changed) rather than waiting for the next unrelated settings edit, so a legacy field doesn't linger in `data.json` indefinitely once it's actually been migrated.

The second entry (v1 → v2) seeds each `mobile*` device-specific field from its desktop counterpart (see "Device-specific settings" below), only for fields actually present in the file and without overwriting a mobile value already there.

If you change the shape of `NotesListSettings` again, append a new function to the end of `SETTINGS_MIGRATIONS` — never edit or remove an old one, since a file could in principle still be sitting at any past version.

### Settings tab layout

`NotesListSettingTab` uses Obsidian's **declarative settings API**: `getSettingDefinitions()` returns plain definition objects and Obsidian renders them itself — there is no `display()` at all. This is what makes every setting show up in Obsidian's in-app settings search (a community plugin review flagged its absence), and it's **why `manifest.json`'s `minAppVersion` is `"1.13.0"`**: the API doesn't exist before that, and deliberately no imperative `display()` fallback is kept for older versions, since that would mean defining every setting twice (name, description, persistence) with the two copies free to drift apart. Don't lower `minAppVersion` without bringing such a fallback back. The definitions are typed `SettingDefinitionItem<keyof NotesListSettings>[]`, so each control's `key` must be a real settings field.

The definitions form `type: "group"` entries, each with a `heading`: "Folder and files", then "Notes list" and "Sidebar", bound to the current device's fields, with an explanatory note row at the top of "Notes list" (see "Device-specific settings" below). The groups' contents:

- **"Folder and files"**: **Folder** (`folder` control) + **Subfolders** (toggle) — where notes are found — then **Template** (`file` control, `filter` limited to `.md`; see "Self-contained note creation" below) and **Unique note name format** (text) — how a *new* note gets created. All four ended up in one group because they're all about the note's location/identity (where it lives, what shape it starts with, what it's named), as opposed to "Notes list"'s per-render concerns.
- **"Notes list"** (formerly "Notes display"): **Show note name** (dropdown), **Content display** (dropdown), **Preview length** (number) — always enabled, even though it only affects rendering when Content display (or a note's own `content-display` override) resolves to `"preview"`; it's independent of that other setting rather than reactively disabled — **Show date group headers** (toggle; see "Date group headers" below) — and **Notes per page** (number), grouped here too since it's just as much a "how the list displays" control as the others. Each dropdown's `options` object carries `satisfies Record<ShowNoteNameMode | ContentDisplayMode, string>`, so adding a new mode to either union without a matching option is a type error.
- **"Sidebar"**: **Tag tree expansion** (dropdown; see "Tag tree expansion" below). Its own group because it's about the right-hand panel, not the notes list itself.

The built-in `folder`/`file` controls bring Obsidian's own vault suggesters, which replaced this plugin's former hand-rolled `FolderSuggest`/`TemplateSuggest` (`AbstractInputSuggest` subclasses, now deleted). The `file` control persists the full path including `.md`, exactly the same format `TemplateSuggest` used to write, so existing `templatePath` values keep working. `folder` leaves `includeRoot` at its default (`false`), since the vault root is already expressed as `""` ("entire vault") and root-as-`"/"` would break that sentinel. Both `number` settings use `min: 1`/`step: 1` plus the exported `validatePositiveInteger()` as `validate`: returning a message rejects the value (shown inline under the setting) instead of persisting it. This replaced the old `bindClampedNumberInput()` helper, which clamped on every keystroke and only re-synced the displayed text on `blur`, to work around an earlier bug where the field couldn't be cleared mid-edit. The framework now owns that input handling.

`getControlValue()`/`setControlValue()` are both overridden instead of relying on `PluginSettingTab`'s defaults. `setControlValue()` writes the value into `plugin.settings` and then always calls `plugin.saveSettings()`, not just `saveData()`, because only `saveSettings()` also triggers `requestRefresh()` to re-render any open Notes List view. It also runs `folderPath`/`templatePath` through `normalizeOptionalPath()`, the same normalization `loadSettings()` applies on every load.

All group headings deliberately avoid the word "settings" (the group is *itself* the settings tab, so a heading like "Folder settings" would be redundant) and use sentence case, not Title Case — both straight from Obsidian's own plugin guidelines for the settings tab; the groups formerly named "Folder settings" and "Notes Display" were renamed to "Folder" (later "Folder and files", once **Template** and **Unique note name format** joined it) and "Notes display" for exactly this reason. "Notes display" was later renamed again to "Notes list", to sit alongside the "Sidebar" group as the two halves of the view.

### Device-specific settings

Every "Notes list" and "Sidebar" setting (`DEVICE_SETTING_KEYS` in `settings.ts`: `showNoteName`, `contentDisplay`, `previewLength`, `showDateGroups`, `notesPerPage`, `tagTreeExpandLevel`) has two values: the plain field is the **desktop** value, and a flat `mobile`-prefixed twin (`mobileNotesPerPage`, …; `deviceSettingKey(key, mobile)` maps between them, typed through a template-literal `MobileSettingKey<K>`) is the **mobile** one. Obsidian has no per-device plugin settings, and `data.json` syncs with the vault, so both live in the same file and the choice happens at runtime: `NotesListPlugin.deviceSettings()` returns `resolveDeviceSettings(settings, Platform.isMobile)`. **Read these settings only through `deviceSettings()`**, never the raw fields, or the view would silently ignore the mobile set. The fields are flat, not a nested `{ desktop, mobile }` object, because the declarative settings API's control `key` has to be a top-level `keyof NotesListSettings`.

The criterion is the *platform* (`Platform.isMobile`: the phone or tablet app), not the pane width that drives the single-column layout (`.is-narrow`, see "Layout"). The two can disagree: a narrow desktop pane uses the single-column layout with desktop settings, and a landscape tablet uses mobile settings in two columns. That's deliberate, since settings follow the device while layout follows the space. The `--notes-list-mobile-*` CSS variables, on the other hand, follow the layout.

In the settings tab, `deviceGroups(mobile)` builds the "Notes list"/"Sidebar" groups bound to one platform's keys. The headings are the same on every device (a per-platform suffix was tried and rejected by the user). Instead the "Notes list" group opens with a "Device-specific settings" note row: a `SettingDefinitionEmpty` item (name + desc, no control), since the declarative API has no description field on a group. Its text names the current device type. `getSettingDefinitions()` includes **only the current device's** set, `deviceGroups(Platform.isMobile)`: each setting appears once, and editing it writes only this device type's field, so mobile values are set from a mobile device. Showing both sets side by side was tried first and rejected by the user as duplicated fields. Mobile defaults equal the desktop ones (tested). To add a new device-specific setting: add its key to `DEVICE_SETTING_KEYS`, add the `mobile*` field and default, include it in `resolveDeviceSettings()`, and add a settings migration seeding the mobile twin.

### Show note name

`shouldShowNoteName(file)` in `view.ts` decides whether `renderEntry()` appends the file name below the date link (`.notes-list-title`): `"never"`/`"always"` are direct; `"whenDifferent"` (the default) shows the name only when `!isUniqueNoteName(file.basename, format)` — i.e. the file has been renamed away from the pattern `NotesListPlugin.uniqueNoteNameFormat()` resolves to (`settings.uniqueNoteNameFormat`, or `DEFAULT_UNIQUE_NOTE_NAME_FORMAT` — `"YYYYMMDDHHmmss"`, from `settings.ts` — when that setting is blank). That method lives on the *plugin*, not the view (`main.ts`, alongside `createUniqueNote()` — see "Self-contained note creation" below), so both note creation and "whenDifferent" detection share one source of truth without the view needing a plugin-internal method call to reach it.

### Self-contained note creation — no "Unique note creator" dependency

The list header's "New Note" button used to invoke Obsidian's core plugin **"Unique note creator"** (internal id `zk-prefixer`) via an undocumented `app.commands.executeCommandById()` surface, and separately read *its* configured naming format for the "whenDifferent" check above — meaning the button silently failed if that core plugin was disabled, and the "when different" mode's detection changed behavior depending on a setting living in a completely different plugin. Neither is true anymore: **this plugin owns note creation and naming entirely, with no dependency on any other plugin being installed or enabled.**

`createUniqueNote()` (and its helpers `uniqueNoteNameFormat()`, `resolveTemplateContent()`) live on `NotesListPlugin` in `main.ts`, not on `NotesListView` — deliberately, so the exact same logic backs both the view's "New Note" button (`newNoteButton.addEventListener("click", () => void this.plugin.createUniqueNote())`) **and** the `"create-new-note"` command registered in `onload()`, which the user can bind to a hotkey from Settings → Hotkeys (no default hotkey is set — see the `main.ts` architecture bullet above for why). The command's callback works with no Notes List view open at all, since nothing it touches (`app`, `settings`) is view-specific.

`createUniqueNote()` now:

1. Resolves the starting content via `resolveTemplateContent()` (below) — empty string if `settings.templatePath` isn't set, the template note's raw content otherwise. Returning `null` (a misconfigured template) aborts the whole operation before anything is created or written — see below.
2. Creates the watched folder (`settings.folderPath`) first if it doesn't exist yet, so the button works even the very first time a folder is configured.
3. Generates the file name itself: `moment().format(uniqueNoteNameFormat())`, passed through `sanitizeFilenameSegment()` (swaps filesystem-illegal characters — `\ / : * ? " < > |` — for a hyphen, since a custom format string could otherwise place e.g. a literal `/` straight into the name and silently create the note in a subfolder). Collisions get a `-2`, `-3`, … suffix, same convention as `generate-test-notes.mjs`.
4. Creates the note directly inside the watched folder (`vault.create()`), so it immediately shows up in the list — not wherever Obsidian's own global "default location for new notes" setting happens to point.
5. Sets `timestamp` to now via `processFrontMatter()` (same safe API as `pinned`), formatted `"YYYY-MM-DDTHH:mm:ss"` — a plain JS string, which Obsidian's own frontmatter writer quotes automatically for the same reason described in "Note dating convention" above. This overwrites whatever placeholder value the template's own `timestamp` property held, while leaving every other property/line the template contributed untouched.
6. Calls `internalMetadataTypeManager(app).setType("timestamp", "datetime")` — the first argument is *our* property name, the second is Obsidian's own fixed internal widget-type name for its "Date & time" picker (an undocumented internal surface, `app.metadataTypeManager`, verified in app.js, that's what Obsidian's own Properties panel calls the moment a property is set through it, persisted to `.obsidian/types.json`). Calling it ourselves means the Properties panel shows the proper date+time picker for `timestamp` immediately, even in a brand new vault with no prior `timestamp` property anywhere and no template configured. This call is wrapped in its **own** try/catch (`console.warn` only, no `Notice`), separate from the outer one around the rest of the method: by this point the note has already been created and correctly dated, so a failure here — the one undocumented-API call in this method that could plausibly break in a future Obsidian release — should degrade to "no auto-registered picker widget," not be reported as "failed to create the note," which would be actively misleading since the note already exists on disk.
7. Opens the new note in the active leaf.

Any failure along the way (folder creation, file creation, frontmatter write) is caught and surfaced as a `Notice` plus a `console.error`, rather than the button silently doing nothing.

#### Template validation

`settings.templatePath` (empty by default — a blank note) points at any markdown note, picked with the settings tab's built-in `file` control (see "Settings tab layout" above). `resolveTemplateContent()` enforces one rule when it's set: the template's own frontmatter must already contain a `timestamp` key — any value, since it's about to be overwritten with "now" regardless — checked via `metadataCache.getFileCache(templateFile)?.frontmatter`, not by parsing raw text. Two distinct failures each abort note creation with their own `Notice` (returning `null`, which `createUniqueNote()` treats as "stop, create nothing" rather than silently falling back to a blank note): the configured path doesn't resolve to a `TFile` at all (deleted/renamed/mistyped since the setting was last saved), or it resolves but has no `timestamp` property. The template's raw content (read via `vault.cachedRead()`, not `metadataCache`, since this is the one place this plugin needs a note's actual body/frontmatter *text*) becomes the new note's starting content verbatim — `processFrontMatter()` then only touches the one `timestamp` key on top of it.

### Tag, date and month filtering

`NotesListView.selectedTag`, `selectedDate`, `selectedMonth`, `searchQuery`/`searchMatches` (see "Full-text search" below) and `tagCollapseOverrides` are transient view state (not persisted to `data.json` — all reset when the view is closed/reopened). `selectedTag` is set from the tag tree under the heatmap panel. It's a `TagFilter` (`tagTree.ts`): a tag path, or the `UNTAGGED` **symbol** for the tree's always-last "Untagged" entry (notes with an empty `tags` array; `renderTagTree()` draws it after the tags, even when there are none, with the count passed in from `render()`). A symbol rather than a magic string, so no real tag can collide with it and `tsc` flags any code that would stringify it (a template literal throws at runtime on a symbol). The filter goes through `noteMatchesTagFilter(tags, filter)`, and its pill label (also used by the empty-list message, see "Localization") special-cases it as `t("tags.untagged")`; `selectedDate` (`"YYYY-MM-DD"`) and `selectedMonth` (`"YYYY-MM"`) are set by clicking a heatmap day cell or a month label, respectively. All three are cleared independently, each via the `x` on its own filter pill in `.notes-list-active-filters` (below the heatmap, `renderFilterPill()` shared by all three) — there's no toggle-off-by-clicking-again anywhere (tag tree, day cell, or month label), by design, so removal always goes through the pill. That container is always created, even with none of the three set, specifically so the Tags section below it doesn't shift up/down as filters are toggled: with nothing active it gets `.is-empty` (`visibility: hidden`, which — unlike `display: none` — keeps its layout box) and one placeholder pill from `renderFilterPill()` (real markup, just invisible) so its reserved height matches an actual pill's rather than a guessed fixed value. `render()` always builds the tag tree and the heatmap from the *full* unfiltered `cachedEntries` (aliased `allEntries` inside `render()`); only the main notes list (`visibleEntries`) is filtered down to notes matching `selectedTag` (via `tagMatchesFilter`) **and** `selectedDate` (exact match on `entry.date.format("YYYY-MM-DD")`) **and** `selectedMonth` (exact match on `entry.date.format("YYYY-MM")`) when set — all three combine with AND, and any subset can be active at once (e.g. selecting a day inside a selected-but-different month just yields an empty list — the pills stay visible so it's clear why, rather than the filters silently overriding each other). The tag index and activity heatmap stay stable reference points regardless of the current filter. Clicking a tag-tree node's chevron records its new state in `tagCollapseOverrides` (see "Tag tree expansion" below) and calls `render()` again like any other interaction (the view always rebuilds its whole DOM rather than patching just the tree — see `src/view.ts`'s `render()`).

### Tasks

The sidebar's Tasks section (`renderTaskPanel()`, below Tags) filters by `selectedTaskFilter: TaskFilter | null` (`"any" | "open" | "done"`), another transient filter combined with AND, with its own pill (`tasks.pill.*`), which the empty-list message also lists. The data is Obsidian's own: `metadataCache`'s `listItems`, where every checkbox list item carries a `task` status character. No text is parsed, and tasks in code blocks are already excluded by Obsidian. Obsidian's search operators (`task:`, `task-todo:`, `task-done:`) aren't a public API, so they can't be reused. `countTasks()` (`tasks.ts`, pure, tested; `TaskListItem` is the structural subset of `ListItemCache` it needs) runs in `rebuildEntries()` into `NoteEntry.tasks`, with the rules agreed with the user: `x`/`X` completed, `-` cancelled (in `total` only, so it matches "any" but neither "open" nor "done"), anything else (`" "`, `/`, …) open. Counts span every note in scope, like the tag counts. The section deliberately reuses the tag tree's classes (`notes-tag-tree-panel`/`-header`/`-list`/`-row`/`-label`/`-count`, plus `notes-task-panel`), so it looks the same. It's built, with Tags, by `renderFilterSections()` (see "Layout"); its content is `renderTaskFilters()`, and it has its own `taskPanelCollapsed`. Each note with open or completed tasks shows `.notes-list-task-count` ("done/(open+done)", Lucide `list-checks`) in its header, pushed next to the pin button by `margin-left: auto`. **Toggling a task in the list.** `MarkdownRenderer.render()` draws clickable checkboxes, but persisting a click is up to the host (Obsidian's reading view does its own), so before this a click only changed the screen. A `click` listener on `.notes-list-content` sends `input.task-list-item-checkbox` clicks to `toggleTask()`. It maps the n-th rendered checkbox to the n-th task line from `metadataCache` `listItems` (sorted by `position.start.line`). That's valid because the rendered body's tasks are always a prefix of the note's: a preview only cuts the end, and `stripInlineTags()` never drops a task line. Checkboxes inside `.internal-embed` belong to another note, so they're excluded from the count and their clicks are undone. It writes through `vault.process()` and `setTaskLineChecked()` (`tasks.ts`, tested), which returns null, so nothing is written, unless the line is a task *and* is currently in the opposite state (Obsidian renders any status but `" "` as checked). That catches a stale or mismatched mapping instead of flipping the wrong task. On null the checkbox is reverted with a `Notice`. Checking sets `x`, unchecking sets `" "`. Line numbers never change on a toggle, so quick successive clicks stay valid before the cache catches up, and the write's own vault events refresh the counts (`keepScroll`). The double-click-to-open handler also skips `input`, so double-clicking a checkbox doesn't open the note.

Checkbox tasks only: TaskNotes-style tasks (one note per task, in frontmatter) aren't list items and aren't counted.

### Open tasks view

The header's title is a **Notes / Open tasks** switch (`NotesListView.mode`, transient, `.notes-list-mode-switch`, as tall as the new-note button so `--nl-header-height` and the sidebar alignment don't change). In `"tasks"` mode `render()` calls `renderOpenTasks(mainEl, visibleEntries)` instead of the notes loop, so the sidebar's search and filters narrow it like the notes, and there's no pagination. It reads only notes whose `NoteEntry.tasks.open > 0`, takes their open task lines from `metadataCache` `listItems` (`isOpenTaskStatus()`, the same rule `countTasks()` uses: not `x`/`X`, not `-`), and the text with `taskLineText()` plus `stripInlineTags()`, since the tags are already the group.

Grouping (`openTasks.ts`, pure, tested): `groupOpenTasks()` puts each task under the **exact combination** of its note's tags (`tagCombination()`: distinct tags via `uniqueTags()`, which now lives in `tagTree.ts`, sorted case-insensitively, first-seen casing). So #work + #alpha is one group, #work alone another, and each task appears once. The user chose this over also listing tasks under each single tag. Nested tags count whole, groups are alphabetical with the untagged one last, and tasks keep the list's note order, then line order.

Each group is one `MarkdownRenderer.render()` of `- [ ] text` lines into a `.notes-list-content.markdown-rendered` box (so checkbox alignment and formatting match the notes), with the first task's note path as source path. After rendering, the n-th `li.task-list-item` (embeds excluded) gets a `.notes-list-task-source` link to its note (date, plus the name when `shouldShowNoteName()` says so). A click on the n-th checkbox maps to the group's n-th task, whose file and line are known exactly, and goes through `writeTaskState()`, shared with the notes list's `toggleTask()`: `vault.process()` + `setTaskLineChecked()`, reverted with a Notice if the line isn't what was rendered. The write's vault events refresh the view, and the checked task drops out.

### Full-text search

A search form (`renderSearchForm()`) sits at the top of the sidebar, above the heatmap: Obsidian's own `.search-input-container` markup (search icon and built-in clear button, so it looks like every other search box in the app) plus a **Search** button, inside a `<form>`. The search runs only on submit (the button, or Enter in the field), never while typing. That was an explicit requirement: each search re-renders the whole view, so it should happen deliberately. The submitted text lives in `NotesListView.searchQuery`, which `render()` writes back into the rebuilt input, and the result in `searchMatches: Set<path> | null` (`null` = no active search). It's a fourth filter alongside tag/date/month, combined with AND, with its own `"query"` pill (`x` → `clearSearch()`). It also appears in `buildEmptyMessage()` and in the heatmap's "x of y notes" count, which falls out of `visibleEntries` for free. Like the other filters it's transient view state.

Speed is the design goal, and it drives the structure. `metadataCache` holds no note text, so `SearchIndex` (`src/searchIndex.ts`) keeps one pre-lowercased string per note (`basename + "\n" + body`, frontmatter stripped via `stripFrontmatter()`), keyed by path along with the `mtime` it was read at. A search is then only an in-memory substring scan: `parseSearchQuery()` lowercases and splits the query into de-duplicated terms, and `matchesAllTerms()` requires every term to appear anywhere in the text. There's no fuzzy matching or ranking: the list stays chronological. `update(files)` re-reads only files whose `mtime` differs from the indexed one, 50 reads at a time via `vault.cachedRead()`. It prunes paths no longer in scope, and logs and skips a file it can't read rather than aborting. Overlapping `update()` calls are serialized through a promise queue, so the background pre-warm and an early search never read the same file twice. Benchmarked on 8,000 synthetic ~3 KB notes (in memory): a search takes ~10 ms, an `update()` with nothing changed ~1.4 ms, and the initial build ~180 ms plus real disk I/O.

`refresh()` keeps the index current. With no search active, it calls `update()` in the background, not awaited, so the list never waits on it. On the view's first open this reads every note in scope once, so even the first search only scans memory; the cost is holding every in-scope note's text in memory for as long as the view is open. With a search active, `refresh()` awaits `update()` (normally just the note(s) whose edit triggered the refresh) and re-runs the search before rendering, so results don't go stale after an edit. `runSearch()` also awaits `update()` before searching, which is normally a no-op after the pre-warm. `searchIndex.ts` imports nothing from Obsidian at runtime (`IndexableFile` is the structural subset of `TFile` it needs), so `test/searchIndex.test.ts` exercises it directly.

**Keyboard access.** `onOpen()` gives the view its own `Scope` (`this.scope = new Scope(this.app.scope)`, the public `View.scope` API), whose shortcuts apply only while the view is focused and take precedence over global hotkeys meanwhile, so nothing changes anywhere else in Obsidian. `Mod+F` focuses the search field; globally it's Obsidian's "Search current file", which only works in an editor and does nothing in this view, so claiming it here loses nothing. `/` does the same, registered with `null` modifiers, because on some layouts `/` itself needs Shift (Shift+7 on an Italian keyboard) and an exact-modifiers registration would never fire there. The handler still ignores real Ctrl/Cmd/Alt chords, and ignores the key entirely when `isEditableTarget()` says focus is in an input/textarea/contenteditable (including the search field itself), so a `/` can still be typed. A bare `f` was considered and rejected: it has the same typing problem as `/` without being a recognizable convention. `focusSearch()` focuses and selects the field. If the field doesn't exist yet (the "Search notes" command opening the view before its first render has finished), it sets `pendingSearchFocus`, which the next `renderSearchForm()` consumes. `activateView()` returns the leaf for that command's sake.

**The field survives re-renders.** `render()` rebuilds the whole DOM, including when the user didn't trigger it (a debounced vault event, a sync). So the unsubmitted text lives in `searchDraft` (updated on every `input` event, reset by `runSearch()`/`clearSearch()`), and `render()` captures whether the old field had focus, plus its selection range, before `contentEl.empty()`, then restores both on the new field. `render()` also builds the sidebar, search form included, *before* awaiting the note bodies' async content fill (`noteRenders`, awaited at the very end), so the field isn't missing from the DOM while those load. Before this, a background refresh mid-typing dropped focus and replaced the draft with the last submitted query.

### Tag note counts

Each tag-tree node shows `(count)` — the number of *distinct notes* matching that tag or one of its nested sub-tags, counted across the **full unfiltered** `allEntries` (same semantics as `tagMatchesFilter`, which the actual filtering uses) — same as the heatmap, the tag tree stays a stable reference point regardless of the current date/month filter, so it does **not** narrow when one is active. Clicking a node combines with any active date/month filter via AND (see "Tag, date and month filtering" above), so it can show *fewer* notes than the count displayed when one of those is also selected — the count is "how many notes carry this tag", not "how many notes clicking it will show right now". This is why `buildTagTree()` takes `allEntries.map((e) => e.tags)` (one array per note) rather than the flattened `allEntries.flatMap((e) => e.tags)` it used before counts existed: with a flat list, a note tagged both `area` and `area/work` would count twice towards `area`'s total. Per note, `buildTagTree()` first collects the *set* of every ancestor path any of its tags reaches (e.g. `area/work` contributes both `"area"` and `"area/work"` to that set), then increments each of those nodes' `count` by exactly 1 — so a note can only ever contribute once to a given node, however many of its tags happen to fall under that node.

### Tag tree expansion

`settings.tagTreeExpandLevel` sets how far the tag tree starts out expanded: `"1"` (fully collapsed: only top-level tags visible), `"2"`/`"3"` (expanded down to that level), or `"all"` (fully expanded; the default, and the only behavior before this setting existed, so upgrading changes nothing). It's a string union rather than a number because the settings dropdown persists its option keys as strings, and "all" needs a value of its own. `isCollapsedByDefault(depth, level)` (`tagTree.ts`, tested) holds the rule: a node at `depth` (1 = top-level tag) is collapsed when `level !== "all" && depth >= Number(level)`. It only matters for nodes with children, since a leaf has nothing to collapse.

The user can still expand/collapse any node by hand. Those clicks are stored in `NotesListView.tagCollapseOverrides` (`Map<path, collapsed>`) as exceptions to the default, rather than as a plain set of collapsed paths (the pre-setting design), because an explicit "expanded" has to be recorded too once the default can be "collapsed". `render()` resolves each node as `overrides.get(path) ?? isCollapsedByDefault(depth, level)`. When the setting changes, `render()` notices (`appliedTagTreeExpandLevel` differs) and clears the overrides, so the new default shows up immediately instead of being masked by earlier clicks. Like the other view state, overrides reset when the view is closed and reopened.

### Pinned notes

Pin state is a `pinned: true`/`pinned: false` property in the **note's own frontmatter**, not plugin data — so it needs no separate storage, survives renames/moves/copies for free (it's part of the file), and is visible/editable directly in the note like any other property. `NotesListPlugin.setPinned(file, pinned)` writes it via `app.fileManager.processFrontMatter()`, Obsidian's own safe read-modify-write helper (creates the frontmatter block if the note doesn't have one yet). Obsidian types that callback's `frontmatter` parameter as `any`, so both `processFrontMatter()` call sites (`setPinned()` and `createUniqueNote()`) annotate it explicitly as `Record<string, unknown>` — otherwise every `frontmatter.x = ...` trips `@typescript-eslint/no-unsafe-member-access`, which the community plugin review flagged. `NoteEntry.pinned` is populated in `rebuildEntries()` from `cache?.frontmatter?.pinned === true`, the same way `date`/`tags` are — a strict `=== true` check, not a truthiness check, so any other value (a string, `1`, etc.) reads as unpinned rather than guessing at intent.

The button itself renders Lucide's `bookmark` icon (not `pin`) regardless of state, and carries Obsidian's own **`clickable-icon`** class (`is-active` when pinned, in place of a custom `is-pinned` class on the button specifically — the row itself still gets `.notes-list-item.is-pinned`, a separate, unrelated concern) rather than reinventing muted/bold-on-hover/active states from scratch. This isn't just a style preference: verified directly by inspecting Obsidian's own bundled `app.css`, a plain custom class alone (no `clickable-icon`) matches its generic `button:not(.clickable-icon)` reset — one type selector plus a `:not()` pseudo-class, which counts as its argument's specificity (a class), so its total specificity beats a single custom class outright, regardless of load order. That's why every color/background rule here used to need `!important` to win at all. Adding `clickable-icon` sidesteps the fight entirely (that reset no longer matches), and its own base/`:hover` rules already provide `var(--icon-color)` at rest and `var(--icon-color-hover)` on hover for free — only the accent-when-pinned color (`.notes-list-pin-button.is-active { color: var(--text-accent); }`) is still layered on top, and even that doesn't need `!important`: it ties on specificity with Obsidian's own `.clickable-icon.is-active` rule (two classes each), and wins on source order since this plugin's stylesheet loads after Obsidian's own. `cursor: pointer` is still explicit, since a plain `<button>` doesn't get a pointer cursor by default the way an `<a>` does (`.clickable-icon` sets `cursor: var(--cursor)`, a theme variable, so this stays as a belt-and-suspenders guarantee rather than relying on that resolving to "pointer").

The pin button's `click` listener is a plain, synchronous callback — `() => void this.togglePin(entry, file)` — that delegates to the `private async togglePin()` method rather than passing an `async` function directly to `addEventListener`: the DOM listener type expects a `void` return, not a `Promise`, and an `async` callback there would still run but leave any rejection (if `setPinned()` ever throws) completely unhandled. `togglePin()` updates `entry.pinned` **in place** on the already-rendered `NoteEntry` immediately after the write, rather than re-reading `getFileCache()` or calling `refresh()`: Obsidian's metadataCache re-parses a frontmatter write asynchronously, so a synchronous re-read right after `await setPinned(...)` could still observe the pre-write value. The vault's own subsequent `modify`/`metadataCache "changed"` events (the write does trigger them, same as any other frontmatter edit) still reach `main.ts`'s normal debounced `refresh()` shortly after, so `cachedEntries` catches up regardless — the in-place update is purely to make the *this* click feel instant rather than waiting on that round trip.

That same async-re-parse lag also broke the **content** rendering for the note whose pin was just toggled, in a more visible way: `renderEntry()` used to find where the body starts via `cache?.frontmatterPosition?.end?.offset` — a byte offset from that same stale-for-a-moment cache. `processFrontMatter` had already rewritten the file (e.g. `pinned: true` → `pinned: false`, one byte shorter) by the time the immediately-following `render()` read it, but the cached offset still described the *previous* frontmatter block's length. Slicing the fresh raw content at the stale offset landed a few bytes into the old block, so `body` started with a stray `-` left over from the closing `---` delimiter — which Markdown renders as a bullet list item, for exactly as long as it took the next real `refresh()` (metadataCache event → debounce) to fix the offset. `stripFrontmatter()` fixes this by deriving the cut directly from the raw content just read (a `^---\n(?:.*\n)*?---\n?` regex) instead of trusting any cache — immune to the race by construction, whether or not the edit was ours. The body group matches whole lines lazily (`(?:.*\r?\n)*?`) rather than `[\s\S]*?` specifically so it also matches zero lines: an earlier version used `[\s\S]*?\r?\n---`, which required a newline *before* the closing `---` that's separate from the one ending the opening line — a completely empty frontmatter block (`---\n---\n`, zero properties) has no such extra newline, so that version silently failed to match and left both `---` lines rendering as a stray bullet.

In `render()`, `filteredEntries` (the tag/date/month result) is partitioned into pinned-then-unpinned via two `Array#filter()` passes rather than a fresh sort — `cachedEntries` is already sorted newest-first and `filter()` is stable, so partitioning alone preserves that order within both groups, at the cost of one extra O(n) pass instead of an O(n log n) sort. Pin status only affects this ordering; it plays no part in whether an entry passes the tag/date/month filter in the first place.

### `refresh()` vs `render()` — why there are two

`NotesListView` splits its single old `refresh()` method in two, because the per-note scan (`app.metadataCache.getFileCache(file)`, `resolveDate()`, `getAllTags()` for *every* note in scope) is the one genuinely expensive step once a folder has thousands of notes — measurably slow (multiple seconds) at ~8000 notes, even though each note's individual cost is small:

- `rebuildEntries()` does that scan once and stores the sorted result in `cachedEntries` (a `TFile` reference + resolved date + tags per note — never file content). It also fixes a redundant double `getFileCache()` call an earlier version had (`resolveDate()` now takes the already-fetched `cache` as a parameter instead of re-fetching it).
- `render()` is everything else — filtering `cachedEntries` by the active tag/date/month, paginating, building the heatmap and tag tree, and rendering the DOM. All of that is proportional to *small* bounded quantities (`notesPerPage`, ~26 heatmap weeks, the unique-tag count), not to the total note count, so it's fast regardless of folder size.
- `refresh()` is now just `rebuildEntries()` + `render()` — kept as the public entry point so `main.ts` (vault events, settings changes) and `onOpen()` don't need to change; they still call something that guarantees fresh data.

**Scroll position.** `render()` empties `contentEl` (the scroll container), which on its own snaps the list back to the top. That's fine after navigation (page change, filters, search), but not for rebuilds the user didn't ask for. Opening a note often triggers one: a metadata event, frequently from another plugin touching files on open, reaches the debounced `refresh()`. So `render({ keepScroll: true })`, used by `refresh()`, the `ResizeObserver` and the readable-line-length listener, restores `scrollTop` after the rebuild. Restoring alone isn't enough: the note bodies fill in asynchronously, so the freshly built list is briefly shorter and the browser would clamp the position. The new `.notes-list-layout` therefore gets the previous `scrollHeight` as an inline `min-height` (`setCssStyles`, which the Obsidian lint rules prefer to `.style`) until `noteRenders` settle, then it's cleared. Every other caller omits the flag. A new background-triggered render must pass it too.

Every interaction that only changes *view* state — clearing or selecting a tag/day/month filter, expanding/collapsing a tag-tree node, changing page, toggling the `readableLineLength` CSS class — calls `render()` directly instead of `refresh()`. None of those can add, remove, or change the metadata of a note, so re-scanning the whole folder for them would be pure waste. If you add a new interaction, ask whether it can possibly change which notes are in scope or their resolved date/tags: if not, wire it to `render()`, not `refresh()`.

### Pagination

`NotesListView.currentPage` (transient, like `selectedTag`) is clamped into `[1, totalPages]` on every `render()` based on `visibleEntries.length` and `settings.notesPerPage`, then `visibleEntries` is sliced to just that page's window (`pageEntries`) **before** calling `renderEntry()` — the only step that actually reads file content (`vault.cachedRead`) and runs `MarkdownRenderer.render`. This is what keeps a large watched folder fast to page through *within* a single `render()`: the expensive-per-`render()` work scales with `notesPerPage`, not with the total note count (`rebuildEntries()`'s one-time scan, above, is the part that scales with total count). `renderPagination()` renders first/previous buttons (`chevrons-left`/`chevron-left`) only off the first page and next/last (`chevron-right`/`chevrons-right`) only off the last one, through one `jumpButton()` helper, and windows the page-number buttons to at most `maxVisiblePages` (10, or 5 in the narrow layout, where 10 plus the four jump buttons overflow a phone screen; 5 plus four is about 290px), sliding to keep `currentPage` inside the window (clamped at both ends so it never shows fewer than that when there are enough pages); the bar also has `flex-wrap: wrap` as a safety net. Since that count is decided in `render()`, not CSS, the `ResizeObserver` that toggles `.is-narrow` also re-renders whenever the threshold is crossed (and only then). Selecting or clearing any of the three filters, and toggling a note's pin (which reorders `visibleEntries`, floating it to/from the top), always resets `currentPage` to 1; other refresh triggers (vault events, settings changes) just re-clamp it, so unrelated background updates don't kick you back to page 1 mid-browsing.

`pageEntries` are rendered by looping and pushing each `renderEntry(mainEl, entry)` call's promise onto an array, then `Promise.all`-ing that array once at the end, rather than a sequential `for...await` loop — safe because `renderEntry()` creates its own `item`/`contentEl` container synchronously before its first `await`, so the loop still appends every entry's container to `mainEl` in page order as it runs; only the async content-fill (the part that actually costs time) runs concurrently instead of one note at a time. Date group headers (below) are inserted into that same loop, synchronously, for the same reason.

### Markdown rendering styles

Each note body's container is `div.notes-list-content.markdown-rendered`. The `markdown-rendered` class is required, not cosmetic: Obsidian's own `app.css` (verified by extracting it from `obsidian.asar`) scopes its table (`.markdown-rendered table`/`th`/`td`), code block (`.markdown-rendered pre`/`code`) and copy-code-button styles under that class. Without it, `MarkdownRenderer.render()`'s output fell back to bare browser styles: unstyled tables, and code blocks without a background plus an always-visible, unstyled copy button. The class's own base rule only sets `tab-size`, so it has no other layout side effects here. Any new element that hosts `MarkdownRenderer` output needs the same class. It isn't the whole story, though: some reading-view rules are scoped to `.markdown-preview-view` instead, which this container deliberately isn't (that class brings the reading view's padding and more). One is the task checkbox's vertical alignment (`position: relative; top: 0.2em; margin-inline-end: 0.6em`), so `styles.css` copies it onto `.notes-list-content .task-list-item-checkbox`; without it the box sat above its text. Check for similar `.markdown-preview-view`-only rules when something in a rendered note looks off. The body's double-click-to-open handler skips targets inside `a, button`, so double-clicking a code block's copy button doesn't also open the note.

### Markdown rendering lifecycle

`renderEntry()` calls `MarkdownRenderer.render(app, body, contentEl, file.path, component)` — that last argument is a `Component`, used by Obsidian to scope whatever the renderer itself registers (event listeners, etc. for the rendered content) so it can be torn down later. It's `this.markdownComponent`, a `Component` the view owns itself — **not** `this.plugin` (an earlier version passed the plugin instance here, flagged by a community plugin review: the plugin's lifecycle spans the entire Obsidian session, so anything registered against it as a "component" would never get cleaned up until the plugin unloads, no matter how many times this note's content gets re-rendered). Since `render()` fully rebuilds the DOM from scratch on every call (see above) but never previously tore down whatever a *previous* pass's `MarkdownRenderer.render()` calls had registered, `render()` now starts by unloading the current `markdownComponent` and replacing it with a fresh one, before any `renderEntry()` calls happen — so each pass's registrations are scoped to *that* pass, not accumulated indefinitely across every re-render for as long as the view stays open. `onClose()` unloads it one final time when the view itself closes.

### Date group headers

`settings.showDateGroups` (default off) shows a `.notes-list-date-group-header` label — "Today", "Yesterday", "This week", or "Older" — above the list wherever consecutive `pageEntries` cross into a new group, via `dateGroupLabel(date)`: today and later folds into "Today" (a future-dated note has no label of its own to fit, and "today or later" avoids inventing a fifth one), exactly yesterday is "Yesterday", on/after `moment().startOf("week")` (locale-aware, same convention `heatmap.ts` uses for its own week columns) is "This week", everything else is "Older". This is computed **per page**, not once over all of `visibleEntries` before slicing — pagination still only depends on `notesPerPage`/`currentPage` (see "Pagination" above), and a group that happens to span a page boundary just shows its header again at the top of the next page rather than the view tracking which group was last shown on the previous one.

Pinned entries are skipped entirely by this loop — no header is shown for one, and it doesn't update `lastGroup` either. Pinned notes already float to their own spot at the top of `visibleEntries` regardless of date (see "Pinned notes" above), so grouping them in with the date-based headers would either show a header out of chronological order (an old pinned note landing ahead of a "Today" note) or make the first *unpinned* entry wrongly skip re-showing a header that only appeared above the pinned block.

### Readable line length

`internalVault(app).getConfig("readableLineLength")` / `.on("config-changed", ...)` — an undocumented internal Vault surface — reads and watches Obsidian's editor-wide "Readable line length" setting, so the notes column's `is-readable-line-width` class (and thus its `max-width: var(--file-line-width)`) mirrors the same core mechanism used by `.markdown-preview-view.is-readable-line-width` (confirmed by inspecting the app's own `app.css`/`app.js`).

### Layout

`.notes-list-view` (the `ItemView`'s `contentEl`) is the single scroll container (`overflow-y: auto`, no padding of its own), so the browser's scrollbar sits at the pane's real right edge, same as any other Obsidian view. The visual inset (`padding: var(--size-4-4)`) lives one level in, on `.notes-list-layout` (the flex row: `.notes-list-main`, flex-grow, and `.notes-list-heatmap-panel`, `flex: 0 0 auto`, sized to its own content and never shrinking).

The heatmap panel is `position: sticky`, with `top` set to exactly where the panel already sits before any scrolling: `.notes-list-layout`'s padding-top plus the sidebar offset below. If `top` didn't match, the panel would visibly slide up by the difference before locking in place on the first scroll (the user reported exactly that once, when only the padding was counted), and it must not move at all. This keeps the heatmap pinned and fully visible while the notes list scrolls past beside it.

The sidebar's first block (the search form) lines up with the list's first item, a date group header or the first note, not with the "Notes" header row. It's pure CSS, with no measuring: `--nl-header-height` (on `.notes-list-view`: `max(--nl-new-note-button-height, title font size × --h4-line-height)`, the first being the header's 28px "+ New note" button) is both `.notes-list-header`'s explicit `height` and, plus the header's `margin-bottom`, the panel's offset (`--nl-sidebar-offset`). That offset is applied twice: as `margin-top`, and added to the sticky `top`, so the panel starts aligned and stays exactly there while scrolling. So the two can't drift, even with a custom `--notes-list-panel-title-font-size`. The narrow layout has no panel at all (see below), so neither applies there. If the header's margin or the button's size changes, update the shared variable/calc.

**Single-column (narrow) layout.** Below `NARROW_LAYOUT_MAX_WIDTH` (720 px, `view.ts`) of *pane* width, `contentEl` gets `.is-narrow`, set by `render()` itself (from `isNarrowLayout()`) and by a `ResizeObserver` registered in `onOpen()` (disconnected through `this.register()`), which re-renders only when the threshold is crossed. It's width-based rather than `Platform.isPhone`/`.is-phone`, so a narrow desktop pane gets it too and a wide landscape tablet doesn't. In that layout `render()` creates **no** `.notes-list-heatmap-panel`: the sidebar's blocks (search form, `.notes-list-activity` = title + heatmap, active filters, tag panel, task panel) are appended straight to `.notes-list-layout`, now a `column`, next to `.notes-list-main`, and `order` sequences them search → heatmap → filters → tags/tasks → notes. This used to be done in CSS alone with the panel as `display: contents`, which the community review warned about ("css-display-contents is only partially supported": an accessibility-tree bug in older Chromium and in WebKit on some elements). It was harmless on a role-less `div`, but the project's rule is to fix review warnings, not keep them. Because the structure now depends on the width, `render()` setting the class itself keeps CSS and DOM in step even on the first pass. That also drops the sidebar's `position: sticky`, which on a phone would pin the heatmap over the list. `.notes-list-layout` has `padding: 0` there (not the two-column `var(--size-4-4)` inset), to give all the width to the content; the heatmap's selection outlines still have room thanks to `.notes-heatmap-scroller`'s own 3px padding (see "Heatmap edge-cell clipping"). The heatmap fills the column's width there: `.notes-heatmap-week` and `.notes-heatmap-month-label` (one per week, so they stay aligned) switch from their fixed 10 px to `flex: 1 1 0`, and the grid's cells to `width: 100%` + `aspect-ratio: 1`, so they scale while staying square (the legend's sample cells keep their fixed size). The empty filters row's reserved height (see "Tag, date and month filtering") is `display: none` there, since nothing below it needs protecting from the shift. The Tags and Tasks sections both go through `renderFilterSections(sidebar, narrow, sections)`. Each section is a title, its collapsed flag (`tagPanelCollapsed`/`taskPanelCollapsed`, transient, default `true`) and a `renderContent(el)` callback. In two columns each section is one `.notes-tag-tree-panel`, title above content, always open, with no click handler. In the narrow layout it builds a `.notes-list-filter-sections` grid (`1fr 1fr`, `order: 4`): first one `.notes-filter-section-header` box per section, side by side at half width (chevron, `.is-collapsed`, accent border when open, click toggles), then one `.notes-filter-section-content` box (`grid-column: 1 / -1`) per *open* section, at full width below. The user asked for exactly that: headers at 50% each, an opened one's content using the whole width. Header and content being separate elements is why this is built in JS per layout, not in CSS. Selecting a tag or a task filter folds its section back, so the filtered list is right there. Notes are also spaced tighter there (`margin-bottom`/`padding-bottom: 1.5rem` instead of the two-column 3rem, pinned notes excepted, as they keep their own boxed spacing).

**Search row in the narrow layout.** `renderSearchForm()` always renders the search button with both an icon span (`.notes-list-search-button-icon`, Lucide `search`) and a label span (`.notes-list-search-button-label`), plus a `.notes-list-search-new-note` button (`type="button"`, so it doesn't submit the form; same `plugin.createUniqueNote()`). CSS picks which ones show: in two columns, the label, with the new-note button hidden (the notes header has its own accent-colored "+ New note" button); in `.is-narrow`, only the icon, and the header's "+ New note" button is hidden in favor of the accent-colored new-note button right of the search button. Both are square, `var(--input-height)` on a side, so they line up with the field, which takes the remaining width. The narrow selectors carry several classes on purpose, to beat Obsidian's `button:not(.clickable-icon)` reset (see "Pinned notes"). This replaced an earlier floating button in the bottom-right corner (`.notes-list-fab`, appended to `containerEl` outside the scroll container), which the user decided against.

### Note typography variables

The note body (`.notes-list-content`, plus its paragraphs' line height), file name (`.notes-list-title`), date link (`.notes-list-datetime`) and section titles (`.notes-list-panel-title`, the "Notes"/"Activity"/"Tags" `h4`s) take their size from public CSS variables meant for users' snippets: `--notes-list-{content-font-size,content-line-height,title-font-size,date-font-size,panel-title-font-size}`, each with a `--notes-list-mobile-*` variant for the narrow layout (documented in the README). `styles.css` never *declares* a public variable, it only reads them with `var()` fallbacks, so a snippet's value wins wherever it's set (`body`, `:root`, `.notes-list-view`) with no specificity fight. The resolution happens once, in internal `--nl-*` variables declared on `.notes-list-view` and redeclared on `.notes-list-view.is-narrow` (mobile variant → regular variant → built-in default); the element rules read only `--nl-*`. Because of that, a snippet has to set the public variables on `.notes-list-view` or an ancestor, not on the element itself. The defaults reproduce the pre-variable look: `1em` (a custom property's value is substituted where it's used, so `1em` there is exactly the inherited size), `1.4rem`, `var(--font-ui-small)`, and `var(--h4-size)` for the section titles, which is what Obsidian's own `h4, .markdown-rendered h4` rule applies (verified in `obsidian.asar`'s `app.css`). That title rule is `.notes-list-view .notes-list-panel-title`, two classes, so it beats Obsidian's bare `h4` rule regardless of load order. Those are the two-column defaults. The narrow layout's own last fallbacks are deliberately a bit larger (content `1.1rem`, file name `1.1em`, section titles `1.1rem`; the user tuned them in `styles.css`), and the README's font table lists both columns, so keep it in sync when changing either. To make another size customizable, add a pair in the same pattern rather than hard-coding a mobile override.

### Heatmap edge-cell clipping

`.notes-heatmap-scroller` sets `overflow-x: auto` for horizontal scrolling of the grid — but per the CSS overflow spec, setting only one axis to a non-`visible` value implicitly computes the other axis (`overflow-y`, left unset) to `auto` as well, so it clips in *both* directions. Selected day cells and month labels are highlighted with `outline`, which paints outside the element's box; without padding on the scroller, cells flush against its edge (first/last week column, top/bottom row) had their outline clipped by that implicit clipping box. `.notes-heatmap-scroller` carries a small `padding: 3px` on every side specifically to leave room for that outline; `padding-bottom` is then further increased (`calc(3px + var(--size-2-2))`) beyond that shared 3px, purely for visual spacing before the `.notes-heatmap-legend` row that follows the scroller as its next sibling — removing the base 3px (on any side) reintroduces the clipping, independent of that extra bottom spacing.

### Text selection

Obsidian sets `body { user-select: none }` globally (confirmed in the app's own `app.css`) and only re-enables it on its own reading/editing views and `[contenteditable]` elements — a custom `ItemView` like this one isn't covered by that allowlist by default. `.notes-list-item` opts back into `user-select: text` explicitly for that reason. Any new custom sub-view added here that should have selectable text needs the same opt-in.

### Known limitations (identified, not fixed)

These were found during a review of the codebase looking for bugs from past reworks, and are deliberately left as-is rather than patched — either because a correct general fix isn't possible/simple, or because fixing them is a design decision rather than a clear-cut bug:

- **A single note edit still triggers a full `rebuildEntries()` rescan** of every note in scope (debounced, via `onVaultEvent()` → `requestRefresh()`), not just the one file that changed — there's no per-file cache patching. Fine at the folder sizes this has been tested at (thousands of notes debounced together), but a genuinely incremental update would need a larger redesign of `cachedEntries` than a quick fix. Left as-is for now.
